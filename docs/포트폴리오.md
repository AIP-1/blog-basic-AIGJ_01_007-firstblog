## 2. 이력서용 문장

### 짧은 버전 (이력서 프로젝트 칸, 3~5줄)
- **OwnLog**: 멀티유저 블로그 플랫폼 1인 개발 및 운영 배포 (Spring Boot 4 · React 19 · PostgreSQL, 2주)
- 타임캡슐을 **새 컬럼 1개와 공개 조건 1줄**로 구현해, 기존 목록 쿼리 6개를 수정 없이 지원(스케줄러 불필요)
- 전체 코드 보안 점검으로 **운영 서버의 인증 우회(URL 인코딩)·파일 삭제 IDOR·오픈 리다이렉트**를 재현하고 수정, 회귀 테스트 추가
- 좋아요·조회수 Lost Update를 **원자적 UPDATE + DB 제약**으로 차단, 동시 100명 요청에서 정확도 100% 검증
- Testcontainers 통합 테스트 169개 + 헤드리스 Chrome 화면 점검 113개, Docker·GitHub Actions 자동 배포, Git Flow·SemVer 도입

### 긴 버전 (포트폴리오·자기소개서용 bullet)
- **설계**: 요구사항 104개를 ID로 명세하고 API 47개를 먼저 확정(API First). 회원:블로그를 1:N으로 설계해 다중 블로그 확장 시 테이블 변경이 필요 없게 했어요.
- **정합성**: "누가 이 글을 볼 수 있는가"를 쿼리 상수 하나와 엔티티 메서드 하나로 모아, 타임캡슐·받는 사람 캡슐 같은 새 규칙을 **한 곳 수정으로** 모든 기능(목록·검색·댓글·좋아요·링크·그래프)에 적용했어요.
- **보안**: 출시 전 전체 점검에서 운영 환경 취약점 3건(인증 우회, IDOR, 오픈 리다이렉트)과 정합성·화면 버그 15건 이상을 찾아 수정하고, 고치지 않은 항목은 근거와 함께 문서화했어요.
- **배포**: 화면과 API를 Docker 이미지 하나로 묶고 GitHub Actions로 자동 배포했어요. 컨테이너가 내부망 DB에 닿지 않던 문제를 **자가 진단 배포 스크립트**로 원인(Docker 네트워크)까지 찾아 해결했어요.
- **품질**: 기능마다 권한 케이스(남의 것·비공개·비로그인) 테스트를 완료 기준으로 두고, 화면 점검이 **제 수정의 오류**까지 잡아내는 회귀 체계를 만들었어요.

## 3. 문제 해결 사례 (STAR)

> 면접에서 가장 많이 묻는 "어려웠던 문제" 답변용이에요. 각 사례는 30초(요약) / 2분(전체) 두 버전으로 말할 수 있게 준비하세요.

### 사례 1. 운영 서버의 인증 우회 취약점을 재현하고 막았어요
| | |
|---|---|
| **Situation** | 출시 전, 백엔드·프론트엔드 전체를 보안·성능·정합성으로 나눠 점검했어요 |
| **Task** | 실제로 악용 가능한 문제를 찾아 **운영에 영향 없이** 확인하고 고쳐야 했어요 |
| **Action** | `/api/users/me`는 401인데 `/%61pi/users/me`(`%61`=a)는 500이 나는 걸 발견했어요. 상태를 바꾸지 않는 GET으로 **운영 서버에서도 재현**했어요. 원인은 인가 규칙이 **디코딩 전 주소**(`getRequestURI`)로 "API가 아니다"라고 판단하고, MVC는 **디코딩 후 주소**로 API를 실행하는 해석 차이였어요. 같은 방식으로 로그인 없이 이미지 업로드도 가능했어요. MVC와 같은 기준으로 비교하는 경로 패턴 매처(`/api/**`)로 바꾸고, MockMvc가 주소를 재인코딩하지 않게 `URI.create`로 보내는 회귀 테스트를 만들었어요 |
| **Result** | 운영에서 같은 요청이 **401**로 막히는 것을 배포 후 확인했어요. 같은 점검에서 IDOR(남의 파일 삭제), 오픈 리다이렉트까지 **보안 8건**을 수정하고 백엔드 테스트를 159 → 169개로 늘렸어요 |
| **배운 점** | 보안 규칙은 실제로 요청을 처리하는 계층과 **같은 해석 기준**을 써야 해요 |

### 사례 2. 배포 실패를 "추측" 대신 "자가 진단"으로 해결했어요
| | |
|---|---|
| **Situation** | 수업 서버에 GitHub Actions로 배포했는데 컨테이너가 `Connect timed out`으로 계속 뜨지 않았어요 |
| **Task** | 서버 접근이 제한된 환경에서 원인을 찾아야 했어요 |
| **Action** | 처음엔 DB 포트 Secret을 의심해 고쳤지만 같은 오류가 났어요. 같은 실패가 반복되자 접근을 바꿔, 배포 스크립트가 **값 형식 → 서버에서 DB 연결 → 컨테이너에서 DB 연결**을 차례로 시험하게 했어요. 결과 `서버 OK / 컨테이너 FAIL`, DB IP가 학교 내부망(10.x)인 걸 보고 Docker 브리지 네트워크에서 내부망 경로가 막힌 걸 확인했어요. `--network host`와 `SERVER_PORT`로 해결했어요 |
| **Result** | 배포에 성공했고, 진단 단계를 남겨 이후 실패는 **원인 메시지와 함께 즉시** 멈춰요(기존: 90초 대기 후 스택트레이스) |
| **배운 점** | 원격 환경 문제는 값을 바꿔 보기 전에 **실패 지점을 나누는 확인을 자동화**하는 게 빨라요 |

### 사례 3. 새 기능이 늘어도 비공개 글이 새지 않는 구조를 만들었어요
| | |
|---|---|
| **Situation** | "볼 수 있는 글" 조건을 쓰는 곳이 목록 8종, 상세, 댓글, 좋아요, 신고, 백링크, 그래프, 잔디까지 계속 늘어났어요. 여기에 "정한 시각까지 봉인"하는 타임캡슐을 추가해야 했어요 |
| **Task** | 한 곳만 빠뜨려도 비공개·봉인 글이 새는 상황에서 **안전하게** 기능을 넣어야 했어요 |
| **Action** | 공개 판단을 쿼리 상수(`PUBLIC_CONDITION`)와 엔티티 메서드(`isViewableBy`) **두 곳**으로 모았어요. 타임캡슐은 개봉 시각을 `published_at`에 넣는 설계로, 새 컬럼 1개와 조건 **1줄**(`published_at <= now()`)로 구현했어요. 받는 사람 캡슐(둘만 보는 편지)도 메서드에 조건 하나를 더하고, DB CHECK 제약으로 "받는 사람이 있으면 비공개"를 이중으로 강제했어요 |
| **Result** | JPQL 목록 쿼리 **6개는 수정 없이** 적용(따로 적힌 네이티브 SQL 1곳만 수정), 스케줄러 없이 자동 공개, 열리는 순간 최신순 맨 위 노출. 기능마다 "새는 경로" 테스트를 둬서 회귀를 막아요 |
| **배운 점** | 보안 조건은 복사되면 언젠가 빠져요. **한 곳에 모으면 새 기능은 재사용만** 하면 돼요 |

### 사례 4. 동시 요청에서도 정확한 좋아요·조회수
| | |
|---|---|
| **Situation** | 인기 글에 동시 요청이 몰리면 엔티티를 "읽고 +1 해서 저장"하는 방식은 값이 사라져요(Lost Update). 설계 단계에서 이 위험을 확인했어요 |
| **Task** | 락 없이 가볍게, 그러면서도 정확하게 세야 했어요 |
| **Action** | 카운터를 **DB가 직접 더하게**(`SET like_count = like_count + 1`) 하고, 엔티티 필드를 `insertable/updatable=false`로 막아 다른 수정이 예전 값으로 덮어쓰지 않게 했어요. 중복 좋아요는 복합 PK + `ON CONFLICT DO NOTHING`, 실제로 저장된 행이 있을 때만 수를 올려요 |
| **Result** | `ExecutorService`·`CountDownLatch` 동시성 테스트: 회원 100명 동시 좋아요 → **100**, 한 회원 10번 연타 → **1**, 50명 동시 조회 → **50** |
| **배운 점** | 단순 증감은 비관적·낙관적 락보다 **원자적 UPDATE + DB 제약**이 가장 싸고 확실해요 |

### 사례 5. 자동 점검이 제 수정의 오류를 잡아냈어요
| | |
|---|---|
| **Situation** | 점검에서 "댓글 등록을 두 번 누르면 두 개 생긴다"를 찾아 `sending` state로 막았어요 |
| **Task** | 수정이 실제로 동작하는지 확인해야 했어요 |
| **Action** | 회귀 화면 점검을 추가했더니 결과가 `0 → 2`로 **여전히 실패**했어요. React state는 다음 렌더링에 바뀌어서, 같은 순간 두 번 클릭하면 두 이벤트가 같은 `false`를 봤어요. **즉시 바뀌는 `useRef`**로 판단하고 state는 버튼 표시에만 쓰게 고쳤어요 |
| **Result** | 같은 순간 두 번 클릭해도 1개만 등록돼요. 화면 점검 105 → 113개, 실행마다 새 브라우저 프로필·별도 DB 스키마로 격리해 결과가 흔들리지 않아요 |
| **배운 점** | "고쳤다"는 확인 전까지 가설이에요. **수정마다 회귀 점검**을 남기는 이유예요 |

> 추가 사례(필요한 회사에 맞춰 교체): 오픈 리다이렉트(브라우저 URL 해석 차이), BCrypt 72바이트 한글 비밀번호 500, 저장된 요약 데이터 마이그레이션, 401 인터셉터 설계, 타임랩스 렌더링 최적화 → [트러블슈팅 기록](트러블슈팅.md) 4·5·8·9·11번

## 4. 기술적 의사결정

| 결정 | 고른 것 | 버린 대안과 이유 |
|---|---|---|
| 타임캡슐 구현 | `published_at` = 개봉 시각 + `sealed_at` | 별도 테이블·스케줄러: 모든 목록 쿼리 수정과 배치 실패 지점이 생겨요 |
| 카운터 동시성 | 원자적 UPDATE + DB 제약 | 비관적 락(대기), 낙관적 락(재시도 처리) |
| 목록 조회 | `select new` DTO 프로젝션 | 엔티티 + fetch join 페이징: 메모리 페이징·본문까지 읽음 |
| 스키마 관리 | Flyway + `ddl-auto: validate` | `ddl-auto: update`: 부분 인덱스·CHECK 불가, 운영 변경 추적 불가 |
| 토큰 저장 | localStorage + sanitize 전제 | HttpOnly 쿠키: CSRF 대응·서버 설정 추가 (2차에 Refresh Token과 재검토) |
| 파일 삭제 권한 (점검 후) | 지우기 전 참조 확인 | 소유자 테이블: 정확하지만 마이그레이션·이관 필요 → 2차 |
| 그래프 렌더링 | d3-force(배치) + Canvas | SVG: 노드 수백 개에서 DOM 비용, 차트 라이브러리: 번들 증가 |
| 배포 단위 | 화면+API 단일 이미지 | 분리 배포: CORS·이중 파이프라인 (수업 서버 포트 1개 제약) |
| 브랜치 전략 | Git Flow + SemVer | GitHub Flow: 더 가볍지만 main 푸시 = 배포라 운영 버전 분리가 필요했어요 |

## 6. 일하는 방식 (AI 협업 포함)

- **API First와 요구사항 ID**: 기획 단계에서 요구사항 104개를 ID로 쪼개고, 코드·테스트·문서가 같은 ID를 가리키게 했어요(예: `(TC-03)`).
- **AI 페어 프로그래밍**: Claude Code에 구현을 맡기되, 정책 결정·설계 승인·검증 기준은 제가 정했어요. `CLAUDE.md`에 작업 권한(삭제·DB 구조·배포 설정은 사전 확인), 코드 규칙, **완료 기준**(권한 테스트, 문서 동기화, CHANGELOG)을 명시해 일관성을 유지했어요.
- **검증 우선**: AI가 만든 코드든 제가 결정한 설계든, 백엔드 통합 테스트와 화면 점검을 통과해야 병합해요.
- **기록**: 트러블슈팅 12건, 점검 보고서, 변경 기록(CHANGELOG), 버전 태그(v0.1.0 ~ v1.0.0)로 의사결정 과정을 남겼어요.

## 7. 회고와 다음 단계

**잘한 점**
- 기능보다 **구조**(공개 조건 일원화, DB 제약)에 먼저 투자해서, 막바지에 기능을 빠르게 늘려도 사고가 나지 않았어요.
- 출시 전에 스스로 **전체 점검**을 해서, 사용자가 겪기 전에 운영 취약점을 찾았어요.

**아쉬운 점과 개선 계획** (README "앞으로의 계획")
| 우선순위 | 항목 | 이유 |
|---|---|---|
