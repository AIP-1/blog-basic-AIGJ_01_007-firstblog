# 소셜 로그인 (카카오 · 네이버 · 구글 · 깃허브)

> OAuth2가 처음인 사람을 위한 문서예요. **개념 → OwnLog의 흐름 → 보안에서 고민한 것 → 키 발급(직접 해야 하는 일)** 순서로 설명해요.
> 키 발급만 필요하면 [5장](#5-키-발급하기-직접-해야-하는-일)으로 바로 가세요.

관련 파일

| 파일 | 하는 일 |
|---|---|
| `backend/.../auth/oauth/OAuthClientRegistrations.java` | 키가 있는 서비스만 골라 OAuth2 설정을 만들어요 |
| `backend/.../auth/oauth/SocialProfile.java` | 서비스마다 다른 회원 정보 모양을 하나로 맞춰요 |
| `backend/.../auth/oauth/SocialLoginService.java` | OwnLog 회원 찾기 / 새로 만들기 |
| `backend/.../auth/oauth/OAuthLoginHandlers.java` | 성공·실패 뒤 화면으로 돌려보내요 |
| `backend/.../auth/oauth/OAuthLoginCodeStore.java` | 60초짜리 1회용 교환 코드 |
| `backend/.../global/config/SecurityConfig.java` | `oauth2Login` 켜기 |
| `backend/src/main/resources/db/migration/V6__social_login.sql` | `user_social_accounts` 테이블, `users.password_set` |
| `frontend/src/components/SocialLoginButtons.jsx` | 로그인·회원가입 화면의 버튼 |
| `frontend/src/pages/OAuthCallbackPage.jsx` | `/oauth/callback` 코드 → 토큰 |

## 1. OAuth2를 한 문단으로

"카카오로 로그인"은 **OwnLog가 사용자의 카카오 비밀번호를 받지 않고**, 카카오에게 "이 사람이 누구인지" 확인받는 방식이에요.
이때 쓰는 표준 약속이 **OAuth 2.0**이고, 그중 웹사이트가 가장 많이 쓰는 방식이 **Authorization Code(인가 코드) 방식**이에요.

| 등장인물 | OwnLog에서는 |
|---|---|
| 사용자 (Resource Owner) | 로그인하려는 사람 |
| 클라이언트 (Client) | OwnLog 서버 |
| 인가 서버 (Authorization Server) | 카카오/네이버/구글/깃허브의 로그인·동의 화면 |
| 리소스 서버 (Resource Server) | 그 서비스의 "회원 정보 주는 API" |

| 용어 | 쉬운 설명 |
|---|---|
| **Client ID** | 서비스에 OwnLog를 등록하면 받는 "앱 번호". 공개돼도 괜찮아요 (동의 화면 주소에 그대로 나와요) |
| **Client Secret** | 앱 비밀번호. **절대 공개하면 안 돼요.** 서버만 알고, GitHub Secrets에만 넣어요 |
| **Redirect URI** | 동의가 끝나면 서비스가 사용자를 돌려보낼 OwnLog 주소. **미리 등록한 주소와 한 글자라도 다르면 거절**돼요 |
| **인가 코드 (code)** | 동의가 끝나면 서비스가 주소에 실어 주는 짧은 표. 서버가 Secret과 함께 내면 액세스 토큰으로 바꿔 줘요 |
| **액세스 토큰** | 그 서비스의 회원 정보 API를 부를 수 있는 열쇠. OwnLog는 회원 정보를 한 번 받고 버려요 |
| **state** | 요청 위조(CSRF)를 막는 무작위 값. 보낼 때 기억해 두고, 돌아올 때 같은 값인지 확인해요 |
| **scope** | "무엇까지 볼게요"라는 권한 범위. 우리는 **닉네임 정도만** 요청해요 |

## 2. OwnLog의 흐름

```
 브라우저                         OwnLog 서버                                카카오
───────────────────────────────────────────────────────────────────────────────────────────
 ① "카카오로 계속하기" 클릭
   GET /oauth2/authorization/kakao ─▶ state를 세션에 기억
                                     302 ─────────────────────────────▶ 동의 화면
 ② 사용자가 동의                                                         │
   GET /login/oauth2/code/kakao?code=…&state=… ◀── 302 ─────────────────┘
                                 ─▶ ③ state 확인 (다르면 실패)
                                     code + Client Secret ──────────────▶ 토큰 발급
                                     액세스 토큰 ───────────────────────▶ 회원 정보 (id, 닉네임)
                                     ④ OwnLog 회원 찾기 / 없으면 만들기
                                     ⑤ 60초짜리 1회용 코드 발급
   302 /oauth/callback#code=… ◀────
 ⑥ 화면이 # 뒤 코드를 읽고 주소에서 지움
   POST /api/auth/oauth/exchange {code} ─▶ 코드 확인(한 번 쓰면 사라짐)
   ◀── { accessToken(JWT), user }          ※ 이메일 로그인과 같은 응답
 ⑦ JWT 저장 → 원래 보던 화면으로
```

①~③은 **Spring Security의 OAuth2 Client**가 다 해 줘요. 우리가 짠 부분은 ④~⑦이에요.

### 2.1 키가 없는 서비스는 꺼져요

Spring Boot의 기본 방식(`spring.security.oauth2.client.registration.*` 설정)은 **client-id가 비어 있으면 서버가 아예 뜨지 않아요.**
우리는 "키를 받은 서비스부터 하나씩 켜고, 하나도 없어도 정상 동작"하고 싶어서 `OAuthClientRegistrations`가 **키가 둘 다 있는 서비스만** 골라 등록해요.

- 하나도 없으면 `oauth2Login` 자체를 켜지 않아요 → `/api/auth/oauth/providers`가 `[]` → 화면에 버튼이 안 보여요.
- 그래서 **키를 넣기 전에 배포해도 안전**하고, 키를 넣고 다시 배포하면 그 버튼이 나타나요.

### 2.2 서비스마다 다른 점

| 서비스 | Spring이 주소를 아나요? | 회원 번호 | 받는 정보 | 특이점 |
|---|---|---|---|---|
| 카카오 | ❌ 직접 적음 | `id` | 닉네임 (`profile_nickname`) | 이메일은 비즈 앱 심사가 필요할 수 있어서 요청하지 않아요. Secret은 `client_secret_post` 방식 |
| 네이버 | ❌ 직접 적음 | `response.id` | 닉네임·이메일 | 회원 정보가 `{"response": {...}}` 안에 한 겹 더 들어 있어요 |
| 구글 | ✅ `CommonOAuth2Provider.GOOGLE` | `sub` | 이름·이메일·`email_verified` | `openid`를 빼서 일반 OAuth2로 받아요 |
| 깃허브 | ✅ `CommonOAuth2Provider.GITHUB` | `id` | 로그인 이름·이름 | 공개 이메일만 와서, 확인 여부를 알 수 없어 쓰지 않아요 |

이 차이를 `SocialProfile.from()` 한 곳에서 맞춰서, 나머지 코드는 서비스 종류를 몰라도 돼요.

### 2.3 처음 온 사람은 이렇게 가입돼요

| 항목 | 정하는 방법 |
|---|---|
| 아이디 (`/@아이디`) | 깃허브 로그인 이름이 규칙(영문 소문자·숫자·`_` 3~20자, 예약어 아님, 안 겹침)에 맞으면 그대로 (`Nay-Oung` → `nay_oung`). 아니면 `kakao_x7k2m9`처럼 서비스 이름 + 무작위 6자 |
| 닉네임 | 서비스의 닉네임/이름 (20자까지). 없으면 "OwnLog 사용자" |
| 이메일 | **확인된** 이메일만 써요. 없으면 `kakao_123@social.ownlog.invalid` (실제로 존재할 수 없는 `.invalid` 도메인) |
| 비밀번호 | 아무도 모르는 임의 값의 해시 + `password_set = false` |
| 블로그·"미분류" | 이메일 가입과 똑같이 한 트랜잭션으로 만들어요 |

> 아이디는 가입 뒤에 바꿀 수 없어요(U-07). 자동 아이디가 마음에 안 들면 이메일로 다시 가입하는 수밖에 없어서, "가입 직후 아이디 고르기 화면"은 [앞으로의 계획](#7-앞으로-할-수-있는-것)에 남겨 뒀어요.

## 3. 보안에서 고민한 것

### 3.1 같은 이메일이어도 자동으로 합치지 않아요

"구글 이메일이 기존 회원 이메일과 같으면 그 계정으로 로그인시켜 주자"는 편해 보이지만 위험해요.
이메일 확인이 느슨한 서비스가 하나라도 있으면, **공격자가 남의 이메일로 소셜 계정을 만들어 그 사람의 OwnLog 계정에 들어갈 수 있어요** (계정 탈취, account pre-hijacking).

그래서

1. **확인된 이메일만** 쓰고 (구글 `email_verified`, 카카오 `is_email_verified`. 깃허브는 확인 여부를 몰라서 아예 안 씀),
2. 그 이메일이 이미 있으면 **연결하지 않고** 로그인 화면으로 돌려보내 "이메일과 비밀번호로 로그인해 주세요"라고 안내해요 (`?oauthError=email_in_use`).

테스트: `SocialLoginTest` 4번 — 확인된 이메일은 막히고, 확인 안 된 이메일은 아예 무시돼서 남의 계정에 닿지 않아요.

### 3.2 JWT를 주소에 싣지 않아요

가장 흔한 구현은 `/oauth/callback?token=eyJ...`처럼 JWT를 주소에 싣는 거예요. 하지만 주소는

- 브라우저 방문 기록에 남고,
- 다른 사이트로 이동할 때 `Referer` 헤더로 새어 나갈 수 있고,
- 서버·프록시 접속 로그에 남아요.

그래서 **60초 동안 한 번만 쓸 수 있는 교환 코드**를 주고, 화면이 `POST`로 코드를 내면 그때 JWT를 **응답 본문**으로 줘요.
코드도 `?` 대신 **`#` 뒤(fragment)** 에 실어요. `#` 뒤는 브라우저가 서버로 보내지 않아서 로그에 남지 않고, 화면은 읽자마자 `history.replaceState`로 주소에서 지워요.
(OAuth2 자체의 "코드 → 토큰" 교환과 같은 생각이에요.)

### 3.3 state와 세션

①에서 만든 state를 ③에서 확인하려면 **두 요청 사이에 어딘가 기억**해야 해요. Spring은 기본으로 **서버 세션**에 둬요.
OwnLog는 원래 세션을 안 쓰는(STATELESS, JWT) 구조지만, 이 몇 초 동안만 세션을 쓰고 성공·실패 직후 `session.invalidate()`로 바로 지워요.
로그인 뒤 인증은 여전히 JWT예요.

> 무중단 배포 중 "동의 화면에 다녀오는 몇 초" 사이에 서버가 blue → green으로 바뀌면 세션이 없어서 그 한 번은 실패해요.
> 다시 누르면 되고, 드문 경우라 받아들였어요 ([배포와-CI-CD.md](배포와-CI-CD.md) 6장).

### 3.4 비밀번호가 없는 회원

| 기능 | 이메일 가입 회원 | 소셜로만 가입한 회원 (`passwordSet=false`) |
|---|---|---|
| 이메일 로그인 | ✅ | ❌ (비밀번호가 없음) |
| 비밀번호 변경 | 현재 비밀번호 확인 | **현재 비밀번호 없이 처음 만들기** → 만든 뒤부터는 이메일 로그인도 돼요 |
| 탈퇴 확인 | 비밀번호 | **내 아이디 입력** |
| 탈퇴 후 | — | 소셜 연결도 지워서, 다시 오면 새 회원으로 가입 |

이메일이 `@social.ownlog.invalid`인 회원은 비밀번호를 만들어도 그 이메일로 로그인할 수 없어서, 설정 화면에서 비밀번호 칸을 숨겨요.

### 3.5 열린 리다이렉트 막기

로그인 뒤 "원래 보던 화면"으로 돌아가는 주소는 `sessionStorage`에 잠깐 두는데, 돌아갈 때 `safeRedirect()`로 **우리 사이트 안의 경로인지** 확인해요 (`//evil.com` 같은 주소 차단, 트러블슈팅 문서의 오픈 리다이렉트 사례와 같은 함수).

## 4. 설정

```yaml
# application.yaml
ownlog:
  oauth:
    public-url: ${PUBLIC_URL:}                # 비우면 요청 주소로 계산 (로컬). 운영은 https://ownlog.java21.net
    clients:
      kakao:  { client-id: ${OAUTH_KAKAO_CLIENT_ID:},  client-secret: ${OAUTH_KAKAO_CLIENT_SECRET:} }
      naver:  { client-id: ${OAUTH_NAVER_CLIENT_ID:},  client-secret: ${OAUTH_NAVER_CLIENT_SECRET:} }
      google: { client-id: ${OAUTH_GOOGLE_CLIENT_ID:}, client-secret: ${OAUTH_GOOGLE_CLIENT_SECRET:} }
      github: { client-id: ${OAUTH_GITHUB_CLIENT_ID:}, client-secret: ${OAUTH_GITHUB_CLIENT_SECRET:} }
```

- 운영(`application-prod.yaml`)은 `public-url`이 `https://ownlog.java21.net`으로 고정이라, 서비스에 등록할 Redirect URI가 항상 같아요.
- 값은 GitHub Secrets → `deploy.yml` → `deploy.sh`의 `docker run -e 이름`으로만 들어가요. **코드·커밋·채팅에 키를 쓰지 마세요.**
- 로컬에서는 루트 `.env`에 같은 이름으로 넣으면 돼요 (`.env`는 커밋되지 않아요).

## 5. 키 발급하기 (직접 해야 하는 일)

모든 서비스에 **Redirect URI**를 이렇게 등록해요. (로컬에서도 시험하려면 두 번째 줄도 함께)

| 서비스 | 운영 Redirect URI | 로컬 Redirect URI |
|---|---|---|
| 카카오 | `https://ownlog.java21.net/login/oauth2/code/kakao` | `http://localhost:5173/login/oauth2/code/kakao` |
| 네이버 | `https://ownlog.java21.net/login/oauth2/code/naver` | `http://localhost:5173/login/oauth2/code/naver` |
| 구글 | `https://ownlog.java21.net/login/oauth2/code/google` | `http://localhost:5173/login/oauth2/code/google` |
| 깃허브 | `https://ownlog.java21.net/login/oauth2/code/github` | (앱 하나에 하나만 돼요. 로컬용 앱을 따로 만들어요) |

### 5.1 카카오 — https://developers.kakao.com
1. 내 애플리케이션 → **애플리케이션 추가하기** (앱 이름: OwnLog).
2. **앱 키**의 **REST API 키** = `OAUTH_KAKAO_CLIENT_ID`.
3. 제품 설정 → **카카오 로그인** → 활성화 **ON**, **Redirect URI** 등록.
4. 카카오 로그인 → **동의항목** → **닉네임**을 "필수 동의"로.
5. 카카오 로그인 → **보안** → **Client Secret 코드 생성**, 활성화 상태 **사용함** = `OAUTH_KAKAO_CLIENT_SECRET`.
6. 앱 설정 → 플랫폼 → **Web** 사이트 도메인에 `https://ownlog.java21.net` 등록.

### 5.2 네이버 — https://developers.naver.com
1. Application → **애플리케이션 등록**.
2. 사용 API: **네이버 로그인**, 제공 정보: **별명**(필수), **이메일**(선택).
3. 로그인 오픈 API 서비스 환경: **PC 웹**, 서비스 URL `https://ownlog.java21.net`, **Callback URL** 등록.
4. 등록 후 **Client ID** / **Client Secret** = `OAUTH_NAVER_CLIENT_ID` / `OAUTH_NAVER_CLIENT_SECRET`.
5. 처음에는 "개발 중" 상태라 **멤버 관리에 등록한 네이버 아이디만** 로그인돼요. 모두가 쓰려면 **검수 요청**이 필요해요 (발표 시연은 멤버 등록으로 충분).

### 5.3 구글 — https://console.cloud.google.com
1. 프로젝트 만들기 → **API 및 서비스** → **OAuth 동의 화면**: 외부(External), 앱 이름·지원 이메일, 범위는 기본(`email`, `profile`)만.
2. 테스트 중(Testing) 상태면 **테스트 사용자**에 등록한 계정만 로그인돼요. 모두가 쓰려면 "앱 게시"(기본 범위만 쓰면 심사 없이 바로 돼요).
3. **사용자 인증 정보** → **OAuth 클라이언트 ID 만들기** → 유형 **웹 애플리케이션**, **승인된 리디렉션 URI** 등록.
4. 클라이언트 ID / 보안 비밀번호 = `OAUTH_GOOGLE_CLIENT_ID` / `OAUTH_GOOGLE_CLIENT_SECRET`.

### 5.4 깃허브 — https://github.com/settings/developers
1. **OAuth Apps** → **New OAuth App** (GitHub Apps 아님).
2. Homepage URL `https://ownlog.java21.net`, **Authorization callback URL** 등록.
3. **Client ID**, **Generate a new client secret** = `OAUTH_GITHUB_CLIENT_ID` / `OAUTH_GITHUB_CLIENT_SECRET`.
   (Secret은 만든 직후 한 번만 보여요. 바로 GitHub Secrets에 넣어요.)

### 5.5 GitHub Secrets에 넣고 배포

저장소 → **Settings → Secrets and variables → Actions → New repository secret**에 위 이름 그대로 넣어요.
그다음 **Actions → Deploy → Run workflow**(또는 main에 새 커밋)로 다시 배포하면 버튼이 나타나요.

확인:
```bash
curl https://ownlog.java21.net/api/auth/oauth/providers
# {"providers":["kakao","naver","google","github"]}
```

## 6. 문제가 생기면

| 증상 | 원인 | 해결 |
|---|---|---|
| 버튼이 안 보여요 | 그 서비스의 ID나 Secret 중 하나라도 비어 있음 | `providers` API로 확인 → Secrets 이름 오타 확인 → 다시 배포 |
| 동의 화면에서 "redirect_uri mismatch" / KOE006 | 등록한 Redirect URI와 다름 (http/https, 끝의 `/`, 서비스 이름) | 5장 표의 주소를 그대로 등록 |
| 돌아오면 "소셜 로그인을 마치지 못했어요" | Secret 틀림, 동의 취소, state 불일치(세션 만료·배포 전환) | 서버 로그 `소셜 로그인 실패:` 확인 후 다시 시도 |
| "이 이메일로 이미 가입한 계정이 있어요" | 3.1의 의도된 동작 | 이메일·비밀번호로 로그인 |
| 네이버·구글에서 "권한 없음" | 개발 중/테스트 상태 | 멤버(테스트 사용자) 등록 또는 검수·게시 |
| 로컬에서 돌아온 뒤 8080 주소로 감 | Vite 프록시를 거치지 않음 | 반드시 `http://localhost:5173`으로 접속해서 시작 (`vite.config.js`에 `/oauth2`, `/login/oauth2` 프록시) |

## 7. 앞으로 할 수 있는 것

- **계정 연결 화면**: 로그인한 상태에서 설정 → "카카오 연결하기"로 기존 회원에 소셜 계정을 안전하게 붙이기 (로그인한 본인이 직접 하는 거라 3.1의 위험이 없어요).
- **가입 직후 아이디 고르기**: 자동 아이디 대신 원하는 아이디를 한 번 고르게.
- **state를 쿠키에**: 서명한 쿠키에 두면 서버를 여러 대로 늘리거나 배포 전환 중에도 끊기지 않아요.
- **프로필 사진 가져오기**: 지금은 받지 않아요(외부 주소를 그대로 쓰면 그 서비스가 사진을 지울 때 깨져서). 받아 와서 우리 업로드 폴더에 저장하는 방식이 필요해요.
