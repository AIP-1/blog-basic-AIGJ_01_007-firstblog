## 1. 개념

### 1-1. multipart/form-data: 파일을 보내는 봉투
보통 API 요청은 JSON 글자로 보내요. 그런데 이미지는 글자가 아니라 **바이트 덩어리**예요. 그래서 파일을 보낼 때는 `multipart/form-data`라는 형식을 써요.
"여러 칸으로 나뉜 봉투"라고 생각하면 돼요. 칸마다 이름(`file`)과 내용(이미지 바이트)이 들어가고, 칸 사이는 경계 문자열(boundary)로 구분해요.

```
POST /api/images
Content-Type: multipart/form-data; boundary=----abc123

------abc123
Content-Disposition: form-data; name="file"; filename="내 사진.png"
Content-Type: image/png

(PNG 바이트들 …)
------abc123--
```
브라우저에서는 `FormData` 객체에 파일을 넣어 보내면 이 형식을 알아서 만들어 줘요.

### 1-2. 왜 확장자나 Content-Type을 믿으면 안 되나: 매직 바이트
위 요청의 `filename="내 사진.png"`와 `Content-Type: image/png`는 **보내는 쪽이 마음대로 적을 수 있는 글자**예요. 악성 스크립트 파일 이름을 `cat.png`로 바꾸면 그대로 통과해 버려요.

그래서 **파일 내용의 맨 앞 몇 바이트**를 직접 확인해요. 이미지 형식마다 첫 바이트가 정해져 있어서 이를 **매직 바이트(매직 넘버)** 라고 불러요. 책 표지는 바꿔 붙일 수 있지만, 본문 첫 페이지를 펼쳐 보면 무슨 책인지 알 수 있는 것과 같아요.

| 형식 | 파일 맨 앞 바이트 |
|---|---|
| JPEG | `FF D8 FF` |
| PNG | `89 50 4E 47 0D 0A 1A 0A` (`‰PNG␍␊␚␊`) |
| GIF | `GIF87a` 또는 `GIF89a` |
| WEBP | `RIFF` + (4바이트 크기) + `WEBP` → 12바이트 |

**SVG는 받지 않아요.** SVG는 그림이지만 사실 XML 글자라서 안에 `<script>`를 넣을 수 있어요(XSS 위험).

### 1-3. UUID 파일 이름
사용자가 올린 파일 이름을 그대로 쓰면 문제가 생겨요.
- 두 사람이 `image.png`를 올리면 **덮어써져요.**
- `../../etc/passwd` 같은 이름으로 **다른 폴더에 쓰려는 공격**이 가능해요.
- 한글·공백·특수문자 때문에 주소가 깨지기 쉬워요.

그래서 서버가 **UUID**(전 세계에서 겹칠 일이 사실상 없는 무작위 36자, 예: `3f9a7c2e-1b4d-4e8a-9c0f-5d2e8b7a6c41`)로 새 이름을 지어 줘요. 사용자가 올린 이름은 저장에 전혀 쓰지 않아요.

### 1-4. 경로 조작(Path Traversal)
`/uploads/../../etc/passwd`처럼 `..`(상위 폴더)를 섞어 **허락된 폴더 밖의 파일**을 읽거나 지우려는 공격이에요. 막는 방법은 "경로를 정리(normalize)한 결과가 여전히 업로드 폴더 안에 있는지" 확인하는 거예요.

### 1-5. 정적 파일 제공과 캐시
올라간 이미지는 그냥 **파일**이라서 매번 코드를 실행할 필요 없이 그대로 돌려주면 돼요(정적 파일 제공). 그리고 브라우저에게 "이 파일은 1년 동안 다시 받지 않아도 돼"라고 알려 주면(`Cache-Control: max-age`) 두 번째부터는 서버에 요청조차 하지 않아 빨라져요.
UUID 이름이라 **같은 주소의 내용이 절대 바뀌지 않기 때문에** 오래 캐시해도 안전해요.

### 1-6. 트랜잭션 커밋 후 삭제 (AFTER_COMMIT)
DB 작업은 실패하면 **롤백**(없던 일로)할 수 있지만, 디스크에서 지운 파일은 되돌릴 수 없어요.
"프로필 사진을 바꾸면서 예전 파일을 지운다"를 생각해 봐요. 파일을 먼저 지웠는데 DB 저장이 실패해서 롤백되면, DB는 **예전 사진 주소를 그대로 가리키는데 파일은 없는** 상태(깨진 이미지)가 돼요.
그래서 "DB 변경이 확정(커밋)된 **뒤에만** 파일을 지운다"로 순서를 정해요.

### 1-7. Docker 볼륨: 컨테이너가 바뀌어도 파일이 남게
Docker 컨테이너 안에 저장한 파일은 **컨테이너를 지우면 같이 사라져요.** 배포할 때마다 컨테이너를 새로 만드니까, 그대로 두면 배포할 때마다 이미지가 전부 날아가요.
그래서 서버의 폴더를 컨테이너 안 폴더에 **연결(마운트)** 해서, 파일은 실제로 서버 디스크에 쌓이게 해요. 이사(새 컨테이너)를 가도 짐(파일)은 창고(서버 폴더)에 남는 셈이에요.

## 2. 전체 흐름 한눈에 보기

```
[브라우저]                                 [Spring Boot]                              [디스크]
 글쓰기: 본문 이미지 / 썸네일
 설정: 프로필 사진
   │ ① 파일 선택 (accept=jpeg,png,gif,webp)
   │ ② uploadImage(file)  ── POST /api/images (multipart, 로그인 필요) ──▶
   │                                        ImageController
   │                                          └ ImageService.upload()
   │                                             ├ 비어 있음?         → 400 INVALID_FILE_TYPE
   │                                             ├ 5MB 초과?          → 400 FILE_TOO_LARGE
   │                                             ├ 확장자 허용 목록?   → 400 INVALID_FILE_TYPE
   │                                             └ 앞 12바이트 매직 검사 → 400 INVALID_FILE_TYPE
   │                                          └ LocalStorageService.store()  ───────▶ {upload.dir}/2026/10/{uuid}.png
   │ ◀── 201 { "url": "/uploads/2026/10/{uuid}.png" } ──
   │ ③ 받은 주소를 본문(![](주소)) / thumbnailUrl / profileImageUrl 에 넣어
   │    글 저장·프로필 저장 요청을 따로 보내요
   │
   │ ④ <img src="/uploads/2026/10/{uuid}.png">  ── GET (로그인 불필요) ──▶
   │                                        WebConfig 리소스 핸들러 ──────────────▶ 파일 읽기
   │ ◀── 이미지 + Cache-Control: max-age=31536000, public (1년) ──
```

중요한 점: **업로드와 사용은 별개의 요청**이에요. 업로드 API는 파일을 저장하고 주소만 돌려줘요. 그 주소를 글이나 프로필에 "붙이는" 건 다음 요청(글 저장, 프로필 저장)이 해요.

## 3. 프론트엔드: 어디서 올리나

API 호출은 한 곳에만 있어요: `frontend/src/api/images.js`
```js
/** API 11.1 이미지 업로드 → "/uploads/2026/10/....png" */
export function uploadImage(file) {
  const form = new FormData()
  form.append('file', file)        // 서버의 @RequestPart("file")와 이름이 같아야 해요
  return api.post('/images', form).then((r) => r.data.url)
}
```
- `api`는 `src/api/client.js`의 axios 인스턴스라서 로그인 토큰(`Authorization: Bearer ...`)이 자동으로 붙어요.
- `FormData`를 넘기면 axios가 `Content-Type: multipart/form-data; boundary=...`를 알아서 정해요. **직접 Content-Type을 적지 않아요** (boundary가 빠져서 서버가 못 읽게 돼요).

이 함수를 쓰는 곳은 세 군데예요.

| 화면 | 파일 | 동작 |
|---|---|---|
| 글쓰기 · 본문에 이미지 넣기 | `pages/WritePage.jsx` | 업로드가 끝나면 **그때의 최신 본문 끝에** `![](주소)`를 붙여요. 업로드하는 동안 쓴 글자가 사라지지 않게 `setForm((f) => ...)` 함수형 업데이트를 써요 |
| 글쓰기 · 썸네일 올리기 | `pages/WritePage.jsx` | `thumbnailUrl`에 주소를 넣어요. "썸네일 빼기"로 `null`로 되돌릴 수 있어요 |
| 설정 · 프로필 사진 바꾸기 | `pages/SettingsPage.jsx` (`ProfileForm`) | 주소를 폼에만 넣고 "[프로필 저장]을 눌러야 반영돼요"라고 알려 줘요 |

파일 선택 창은 `<input type="file" accept="image/jpeg,image/png,image/gif,image/webp" hidden>`이에요. `accept`는 **선택 창에서 보이는 파일을 거르는 편의 기능일 뿐**, 보안 검사가 아니에요. 진짜 검사는 서버가 해요.
글쓰기 화면은 선택 후 `e.target.value = ''`로 입력을 비워서, 같은 파일을 다시 골라도 업로드되게 해요.

## 4. 백엔드: 검사하고 저장하기

### 관련 파일
| 파일 | 역할 |
|---|---|
| `backend/src/main/java/com/ownlog/image/controller/ImageController.java` | `POST /api/images` (multipart) → 201 |
| `.../image/service/ImageService.java` | 크기 → 확장자 → 매직 바이트 순서로 검사 |
| `.../image/dto/ImageUploadResponse.java` | 응답 `record ImageUploadResponse(String url)` |
| `.../global/storage/ImageType.java` | 허용 형식(JPEG·PNG·GIF·WEBP)과 매직 바이트 판별 |
| `.../global/storage/StorageService.java` | 저장소 인터페이스 (`store`, `delete`) |
| `.../global/storage/LocalStorageService.java` | 서버 디스크에 저장하는 구현체 |
| `.../global/storage/UploadProperties.java` | `ownlog.upload.dir` 설정 |
| `.../global/error/GlobalExceptionHandler.java` | Spring의 업로드 크기 초과 예외 → `FILE_TOO_LARGE` |
| `backend/src/test/java/com/ownlog/image/ImageApiTest.java` | 업로드 테스트 |

### 4-1. 인증
`SecurityConfig`에서 `/api/**`는 로그인이 필요해요. 그래서 업로드는 로그인한 사람만 할 수 있어요(비로그인 401). 반대로 이미지를 **보는** `GET /uploads/**`는 누구나 가능해요.

### 4-2. 검사 순서 (`ImageService.upload`)
| 순서 | 검사 | 실패하면 |
|---|---|---|
| 0 | Spring이 먼저: 파일 5MB, 요청 전체 6MB 초과 (`spring.servlet.multipart.*`) | `MaxUploadSizeExceededException` → **400 `FILE_TOO_LARGE`** |
| 1 | 비어 있는 파일 | 400 `INVALID_FILE_TYPE` |
| 2 | 크기 > 5MB (`MAX_SIZE`, 위에서 막히지만 한 번 더) | 400 `FILE_TOO_LARGE` |
| 3 | 파일 이름 확장자가 `jpg, jpeg, png, gif, webp` 중 하나인가 (대소문자 무시) | 400 `INVALID_FILE_TYPE` |
| 4 | 앞 12바이트(`HEAD_SIZE`)가 허용 형식의 매직 바이트인가 | 400 `INVALID_FILE_TYPE` |

에러 메시지는 `ErrorCode`에 있어요: `"jpg, png, gif, webp 파일만 올릴 수 있어요."`, `"5MB 이하의 파일만 올릴 수 있어요."`

**저장할 확장자는 실제 내용 기준이에요.** 이름은 `photo.png`인데 내용이 JPEG면 받아 주되 `.jpg`로 저장해요. 테스트 `extensionFollowsContent`가 이걸 확인해요. 거꾸로 `cat.png`라는 이름의 스크립트, `logo.svg`, `virus.exe`, 빈 파일은 모두 400이에요 (`rejectsNonImages`).

### 4-3. 저장 (`LocalStorageService.store`)
```java
LocalDate today = LocalDate.now(ZoneId.of("Asia/Seoul"));        // 폴더 날짜는 한국 기준
String relative = "%d/%02d/%s.%s".formatted(
        today.getYear(), today.getMonthValue(), UUID.randomUUID(), extension);
// → "2026/10/3f9a7c2e-....png"
Files.createDirectories(target.getParent());
Files.copy(content, target);
return "/uploads/" + relative;                                    // 응답 주소
```
- 저장 위치: `{ownlog.upload.dir}/연/월/UUID.확장자`
- 연·월 폴더로 나누는 이유: 한 폴더에 파일이 수만 개 쌓이면 다루기 불편해서예요.
- 디스크 오류는 500으로 나가요 (사용자에게 내부 정보는 보이지 않아요).

### 4-4. 저장소를 인터페이스로 둔 이유
`StorageService`는 인터페이스이고, 지금 구현은 서버 디스크(`LocalStorageService`) 하나예요. 나중에 클라우드 저장소(예: Cloudinary, S3)로 옮기면 **구현체만 새로 만들면** `ImageService`는 고치지 않아도 돼요. (클라우드 구현은 아직 없어요.)

## 5. 이미지 보여주기 (정적 파일 제공과 캐시)

`backend/src/main/java/com/ownlog/global/config/WebConfig.java`
```java
registry.addResourceHandler("/uploads/**")
        .addResourceLocations(location)                                    // file:{upload.dir 절대 경로}/
        .setCacheControl(CacheControl.maxAge(Duration.ofDays(365)).cachePublic());
```
- 주소 `/uploads/2026/10/x.png` ↔ 파일 `{upload.dir}/2026/10/x.png`
- 응답에 `Cache-Control: max-age=31536000, public`(1년)이 붙어요.
- 지금은 **Spring이 직접** 파일을 돌려줘요. 코드 주석에도 있듯 Nginx가 직접 제공하게 바꾸면 더 빨라지지만, 아직 그렇게 하지 않았어요.

개발 중(프론트 5173, 백엔드 8080)에는 `frontend/vite.config.js`의 프록시가 `/uploads` 요청도 8080으로 넘겨 줘요. 그래서 `<img src="/uploads/...">`가 그대로 동작해요. 운영에서는 화면과 API가 같은 주소라 프록시가 필요 없어요.

## 6. 썸네일 자동 지정

글 카드에 보이는 썸네일은 이렇게 정해져요 (P-02).

```
글 저장 요청의 thumbnailUrl
   ├ 값이 있음 → 그대로 사용 (단, "/uploads/" 또는 "https://"로 시작해야 해요. 아니면 400)
   └ null     → 본문에서 첫 번째 ![설명](주소)의 주소
                  ├ "/uploads/" 또는 "https://"로 시작하고 500자 이하 → 썸네일
                  └ 그 밖(http://, data:, javascript: 등) → 썸네일 없음
```
| 위치 | 코드 |
|---|---|
| 직접 지정 검증 | `post/dto/PostRequest.java`, `DraftRequest.java`: `@Pattern(regexp = "^(/uploads/|https://).*")` |
| 자동 지정 | `post/domain/Post.java`의 `resolveThumbnail()` → `global/util/MarkdownText.firstImageUrl()` |

`http://`를 막는 이유: https 사이트에 http 이미지를 넣으면 브라우저가 "혼합 콘텐츠" 경고를 내거나 막아요. 그리고 엉뚱한 스킴(`javascript:` 등)을 카드 `<img>`에 넣지 않기 위해서예요. 이 규칙은 `v0.6.0`의 보안 수정(`http://` 썸네일)에서 통일됐어요.

프로필 사진은 더 엄격해요: `ProfileUpdateRequest`에서 `^/uploads/.*`만 허용해요 (외부 주소 불가).

## 7. 파일 지우기

### 7-1. 언제 지우나 (지금 구현된 것)
| 상황 | 파일 삭제? | 위치 |
|---|---|---|
| 프로필 사진을 다른 사진으로 바꾸거나 "사진 지우기" 후 저장 | ✅ 예전 파일 삭제 (아래 조건) | `UserService.updateProfile()` |
| 회원 탈퇴 | ✅ 프로필 사진 삭제 (아래 조건) | `UserService.withdraw()` |
| 글 삭제 | ❌ 본문·썸네일 이미지 파일은 **지우지 않아요** | `PostService.delete()`는 DB 행만 지워요 |
| 글 수정으로 이미지를 본문에서 뺌 | ❌ 지우지 않아요 | |
| 업로드만 하고 글을 저장하지 않음 | ❌ 지우지 않아요 | |

> README "앞으로의 계획" 표의 "글 삭제 후 파일 삭제 이벤트"는 **삭제 이벤트 구조(`ImageDeleteEvent`)가 준비돼 있다**는 뜻이에요. 현재 코드에서 이 이벤트를 쓰는 곳은 프로필 사진(변경·탈퇴)뿐이고, 글 삭제에는 연결되어 있지 않아요.

### 7-2. 커밋 후에만 지우기
```java
// UserService: 지울지 결정만 하고 "지워 주세요" 이벤트를 발행
eventPublisher.publishEvent(new ImageDeleteEvent(url));

// ImageDeleteListener: 트랜잭션이 커밋된 뒤에만 실행 (롤백되면 아예 실행되지 않아요)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onImageDelete(ImageDeleteEvent event) {
    storageService.delete(event.url());
}
```
```
updateProfile() 트랜잭션 ──────────────────────────┐
  ├ DB: profile_image_url = 새 주소                 │
  └ 이벤트 발행: "예전 파일 지워 줘" (아직 대기)       │
                                         커밋 성공? ─┤
                     ├ 예 → ImageDeleteListener 실행 → 파일 삭제
                     └ 아니오(롤백) → 리스너 실행 안 함 → 파일 그대로 (DB도 예전 주소 그대로라 일치)
```

`LocalStorageService.delete()`의 안전장치
- `/uploads/`로 시작하지 않는 주소(외부 `https://...`)는 우리 파일이 아니라서 무시해요.
- 경로를 정리(`normalize()`)한 뒤 업로드 폴더 밖이면 지우지 않고 경고 로그만 남겨요 → **경로 조작 차단**.
- 파일 삭제가 실패해도 사용자 요청은 성공으로 끝나요 (로그만 남겨요).

### 7-3. 아직 쓰이는 파일은 지우지 않기: `ImageReferenceChecker`
**이 장치가 생긴 이유는 실제 보안 버그 때문이에요** ([`docs/트러블슈팅.md` 3번](../트러블슈팅.md)).

버그(IDOR, 남의 대상에 대한 권한 검사 누락)
1. 프로필 사진 주소는 "`/uploads/`로 시작하는가"만 검사했어요. 업로드한 사람은 기록하지 않았어요.
2. 공격자가 **남의 글에 있는 이미지 주소**를 자기 프로필 사진으로 저장해요.
3. 그다음 프로필 사진을 바꾸면 → 서버는 "예전 프로필 사진"이라고 생각하고 **그 파일을 지워요.**
4. 원래 주인의 글 이미지가 깨져요.

해결: 지우기 전에 **다른 곳에서 쓰는지** DB에서 확인하고, 쓰고 있으면 지우지 않아요.
```sql
SELECT EXISTS (SELECT 1 FROM users WHERE profile_image_url = ? AND id <> ?)     -- 다른 회원의 프로필
    OR EXISTS (SELECT 1 FROM posts WHERE thumbnail_url = ? OR content LIKE ?)  -- 글 썸네일·본문
```
- `LIKE` 패턴에 들어가는 `%`, `_`, `\`는 이스케이프해서, 주소 안의 글자가 와일드카드로 해석되지 않게 해요.
- 가장 정확한 방법은 업로드 테이블(`uploads(url, user_id)`)로 주인을 기록하는 것이지만, 마감 직전이라 마이그레이션 없이 바로 막을 수 있는 이 방법을 골랐어요. 회귀 테스트 2개(남의 파일은 남고, 아무도 안 쓰는 내 사진은 지워짐)가 있어요.

## 8. 운영 서버에서의 저장 위치

```
서버(s2.java21.net)                          컨테이너(ownlog)
~/ownlog-uploads/   ◀── docker run -v ──▶   /app/uploads/   ← ownlog.upload.dir (application-prod.yaml)
  └ 2026/10/xxx.png                            └ 2026/10/xxx.png
```
| 어디서 | 무엇을 |
|---|---|
| `backend/src/main/resources/application-prod.yaml` | `ownlog.upload.dir: /app/uploads` |
| `Dockerfile` | `/app/uploads` 폴더를 만들고 앱 사용자에게 권한을 줘요 |
| `deploy/deploy.sh` | `UPLOAD_DIR="$HOME/ownlog-uploads"`, `mkdir -p`, `-v "$UPLOAD_DIR:/app/uploads"`, `--user "$(id -u):$(id -g)"` |

- `--user`로 서버 계정 권한으로 실행해서, 컨테이너가 서버 폴더에 파일을 쓸 수 있어요.
- 배포할 때 `docker rm -f`로 컨테이너를 지워도 `~/ownlog-uploads`는 그대로라 이미지가 남아요.
- 로컬 개발에서는 기본값 `./uploads`예요 (실행 위치 기준, 보통 `backend/uploads/`). `.gitignore`에 `uploads/`가 있어서 커밋되지 않아요.
- 테스트는 `build/test-uploads`에 저장해요 (`application-test.yaml`).

## 9. 설정 값 모음

| 설정 | 값 | 위치 | 뜻 |
|---|---|---|---|
| `spring.servlet.multipart.max-file-size` | `5MB` | `application.yaml` | 파일 하나 최대 크기 |
| `spring.servlet.multipart.max-request-size` | `6MB` | `application.yaml` | 요청 전체 최대 크기 (파일 + 나머지) |
| `ImageService.MAX_SIZE` | 5MB | 코드 상수 | 서비스에서 한 번 더 검사 |
| `ownlog.upload.dir` | `${UPLOAD_DIR:./uploads}` | `application.yaml` | 로컬 저장 폴더 (`UPLOAD_DIR` 환경 변수로 바꿀 수 있어요) |
| `ownlog.upload.dir` | `/app/uploads` | `application-prod.yaml` | 운영 컨테이너 안 폴더 |
| `ownlog.upload.dir` | `build/test-uploads` | `application-test.yaml` | 테스트용 |
| Nginx `client_max_body_size` | `20M` (배포 설명서 기준) | 서버 `~/nginx/ownlog.java21.net.conf` (저장소 밖) | Nginx가 받는 요청 최대 크기 |

Nginx 설정 파일은 이 저장소에 없고 수업 서버에 있어요. 바꾸려면 강사님께 반영을 요청해야 해요 (CLAUDE.md 10장). Nginx의 **기본값은 1MB**라서, 이 값이 없거나 작으면 1MB 넘는 이미지는 Spring까지 오지도 못하고 Nginx가 413을 돌려줘요 (API 명세서 11.1의 주의 문구).

```
요청 크기 제한은 "바깥부터" 걸려요
브라우저 ──▶ Nginx (client_max_body_size) ──▶ Spring (max-request-size 6MB, max-file-size 5MB) ──▶ ImageService (5MB)
             넘으면 413 (HTML 응답)              넘으면 400 FILE_TOO_LARGE (JSON)                넘으면 400 FILE_TOO_LARGE
```

## 11. FAQ

**Q. 운영에서 큰 사진을 올리면 413 에러가 나요.**
413(Payload Too Large)은 **Nginx**가 보낸 응답이에요 (Spring은 크기 초과를 400 `FILE_TOO_LARGE`로 보내요). Nginx의 `client_max_body_size`가 작게 설정됐는지 확인하고, 바꿔야 하면 강사님께 요청해요. 413 응답은 JSON이 아니라서 화면에는 "서버에 연결할 수 없어요" 같은 기본 문구가 보일 수 있어요.

**Q. 5MB 조금 넘는 파일을 올리면 어떻게 돼요?**
Spring의 `max-file-size`가 먼저 막고, `GlobalExceptionHandler`가 400 `FILE_TOO_LARGE`("5MB 이하의 파일만 올릴 수 있어요.")로 바꿔 줘요.

**Q. 배포했더니 예전에 올린 이미지가 깨져요.**
확인 순서
1. `deploy.sh`의 `-v "$UPLOAD_DIR:/app/uploads"`가 그대로인가 (빠지면 컨테이너 안에만 저장돼 배포 때 사라져요)
2. 서버의 `~/ownlog-uploads/연/월/`에 파일이 실제로 있는가
3. `application-prod.yaml`의 `ownlog.upload.dir`이 `/app/uploads`인가
4. 이미지 주소가 `http://localhost:8080/uploads/...`처럼 **다른 서버 주소**로 저장되진 않았나 (로컬 DB 데이터를 옮긴 경우)

**Q. 로컬에서 올린 이미지가 서버에는 없어요.**
정상이에요. 로컬은 `backend/uploads/`, 서버는 `~/ownlog-uploads/`로 **완전히 다른 폴더**예요. DB도 따로예요.

**Q. 이름이 `.png`인데 "jpg, png, gif, webp 파일만…" 에러가 나요.**
파일 **내용**이 PNG가 아닌 거예요. 예: HEIC(아이폰 기본 형식) 사진의 확장자만 바꾼 경우, 또는 스크린샷 도구가 다른 형식으로 저장한 경우. 이미지 편집기에서 PNG/JPEG로 다시 저장해서 올려요.

**Q. SVG 로고는 왜 안 돼요?**
SVG 안에 스크립트를 넣을 수 있어서(XSS) 일부러 막았어요 (`ImageType` 주석).

**Q. 글을 지웠는데 이미지 주소로 들어가면 아직 보여요.**
지금은 글을 지워도 이미지 파일은 지우지 않아요 (7-1). 또 1년 캐시 때문에 브라우저에 남아 있을 수도 있어요.

**Q. 프로필 사진을 바꿨는데 예전 파일이 안 지워졌어요.**
다른 회원의 프로필이나 어떤 글(썸네일·본문)이 같은 주소를 쓰고 있으면 일부러 지우지 않아요 (7-3). 또는 DB 저장이 실패(롤백)했다면 지우지 않아요 (7-2).

**Q. 업로드 API를 curl로 시험해 보고 싶어요.**
```bash
TOKEN=...   # 로그인 응답의 accessToken
curl -i -H "Authorization: Bearer $TOKEN" -F "file=@./photo.png" http://localhost:8080/api/images
# HTTP/1.1 201 ... {"url":"/uploads/2026/10/....png"}
```
`-F`가 multipart/form-data로 보내 줘요. 이름은 꼭 `file`이어야 해요.
