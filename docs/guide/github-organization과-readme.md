## 1. GitHub Organization이란

GitHub 계정에는 두 종류가 있어요.

| | 개인 계정 (Personal account) | Organization (조직) |
|---|---|---|
| 주인 | 한 사람 | 여러 사람이 함께 (회사, 동아리, **수업**) |
| 저장소 주소 | `github.com/내아이디/저장소` | `github.com/조직이름/저장소` |
| 로그인 | 할 수 있어요 | 못 해요. 사람(개인 계정)이 조직의 **멤버**로 들어가요 |
| 권한 관리 | 저장소마다 협업자를 한 명씩 초대 | 멤버·팀 단위로 저장소 권한을 한꺼번에 관리 |
| 비유 | 내 집 | 학교 건물 (학생마다 교실 열쇠 권한이 달라요) |

Organization을 쓰는 이유
- 강사님(관리자)이 모든 학생의 저장소를 **한곳에서** 보고 관리할 수 있어요.
- 학생이 수업을 마쳐도 저장소는 조직에 남아요.
- 조직 전체에 공통 규칙(기본 권한, 브랜치 규칙, 공용 Secrets 등)을 걸 수 있어요.

## 2. 역할과 권한

### 조직 안에서의 역할
| 역할 | 할 수 있는 것 |
|---|---|
| **Owner** | 조직 전체 관리: 멤버 초대·삭제, 결제, 모든 저장소 설정 |
| **Member** | 조직에 속한 사람. 저장소에 무엇을 할 수 있는지는 아래 저장소 권한으로 정해져요 |
| Outside collaborator | 조직 멤버는 아니지만 특정 저장소에만 초대된 사람 |

### 저장소 하나에 대한 권한 (약한 순)
| 권한 | 할 수 있는 것 |
|---|---|
| **Read** | 코드 보기, 이슈 쓰기 |
| **Triage** | + 이슈·PR 분류(라벨, 담당자) |
| **Write** | + **푸시**, PR 병합 |
| **Maintain** | + 저장소 일부 설정 (Secrets·삭제 같은 민감한 설정은 제외) |
| **Admin** | + **모든 설정**: Secrets, 브랜치 보호, 협업자 초대, 저장소 삭제 |

> 저장소의 **Settings** 탭이 안 보이거나 일부 메뉴가 비어 있다면, 내 권한이 Admin이 아닌 거예요. 그때는 조직 Owner(강사님)께 요청해야 해요.

## 3. 이 저장소와 AIP-1 Organization

```bash
git remote -v
# origin  https://github.com/AIP-1/blog-basic-AIGJ_01_007-firstblog.git
```
- 이 저장소는 **`AIP-1`** 이라는 Organization 아래에 있어요. 수업용 조직이에요.
- 저장소 이름 `blog-basic-AIGJ_01_007-firstblog`는 수업에서 정해 준 형식이에요. 그래서 프로젝트 이름(OwnLog)과 달라요.
- CHANGELOG 맨 아래의 버전 비교 링크도 이 주소를 써요: `https://github.com/AIP-1/blog-basic-AIGJ_01_007-firstblog/compare/v1.0.1...v1.1.0`

내 권한 확인: GitHub에서 저장소를 열었을 때 **Settings** 탭이 보이면 Admin이에요. 조직 멤버 목록·역할은 `https://github.com/orgs/AIP-1/people`에서 볼 수 있어요(권한에 따라 보이는 범위가 달라요).

> 조직의 기본 권한, 저장소 공개 범위, 조직 차원의 규칙이 실제로 어떻게 설정됐는지는 이 저장소 안의 파일로는 알 수 없어요. GitHub 화면에서 직접 확인해야 해요.

## 4. 저장소 공개 범위

| 공개 범위 | 누가 볼 수 있나 |
|---|---|
| **Public** | 인터넷의 누구나 (포트폴리오로 보여 주기 좋아요) |
| **Private** | 초대받은 사람·권한 있는 조직 멤버만 |
| Internal | (기업용 플랜) 같은 기업의 멤버 |

확인·변경: 저장소 → **Settings → General → 맨 아래 Danger Zone → Change repository visibility**. 조직 저장소는 조직 설정에 따라 학생이 바꿀 수 없을 수 있어요.

공개 저장소라면 특히
- `.env`, DB·SSH 비밀번호, JWT 비밀키 같은 비밀값을 절대 커밋하지 않아요 (`.gitignore`에 `.env`가 있어요).
- 배포 설명서 PDF(`docs/서버 배포 설명서*.pdf`)는 커밋하지 않아요 (CLAUDE.md 5장).
- 한번 커밋된 비밀값은 지워도 **이력에 남아요.** 값을 바꾸는 수밖에 없어요.

## 5. Secrets: 비밀값 보관함

### 개념
GitHub Actions가 배포하려면 서버 비밀번호, DB 비밀번호가 필요해요. 그렇다고 `deploy.yml`에 적으면 누구나 볼 수 있어요.
**Secrets**는 GitHub이 암호화해서 보관하는 비밀값이에요. 워크플로에서 `${{ secrets.이름 }}`으로만 꺼내 쓸 수 있고, 로그에 찍히면 자동으로 `***`로 가려져요. 한번 저장하면 **값을 다시 볼 수 없고**(덮어쓰기만 가능), 이름만 보여요.

위치: 저장소 → **Settings → Secrets and variables → Actions → Repository secrets**

| 종류 | 범위 |
|---|---|
| Repository secrets (이 프로젝트) | 이 저장소에서만 |
| Organization secrets | 조직의 여러 저장소가 함께 (Owner가 설정) |
| Environment secrets | 특정 환경(예: production)에서만 |

### 이 저장소가 쓰는 Secrets (이름만)
`deploy.yml`에서 `secrets.`로 참조하는 이름이에요. **값은 이 문서에도, 어디에도 적지 않아요.**

| 이름 | 용도 | 쓰는 단계 |
|---|---|---|
| `SSH_ADDRESS`, `SSH_ID`, `SSH_PASSWORD`, `SSH_PORT` | 배포 서버 접속 | 파일 전송(scp), 배포 스크립트 실행(ssh) |
| `DB_ADDRESS`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`, `DB_SCHEMA` | 수업 DB 접속 | 서버의 `deploy.sh` → `docker run -e` |
| `JWT_SECRET` (선택) | 로그인 토큰 서명 키 | 없으면 서버에서 한 번 만들어 계속 사용 (`deploy.sh`) |

흐름
```
GitHub Secrets ──▶ deploy.yml (env:, with:) ──▶ SSH로 서버 접속 ──▶ deploy.sh의 환경 변수 ──▶ docker run -e 이름
                                                                 (값이 비면 "❌ ○○ 값이 비어 있어요"로 멈춤)
```
- `ci.yml`(테스트만)은 Secrets를 쓰지 않아요. 테스트는 `application-test.yaml`과 Testcontainers로 돌아가요.
- Secret 값을 붙여 넣을 때 **앞뒤 공백·줄바꿈**이 섞이면 실패해요. `deploy.sh`가 `DB_PORT`(숫자만인지)와 `DB_ADDRESS`(공백, `http://`, `:포트`가 섞였는지)를 검사해서 알려 줘요.

## 6. Actions 탭 보는 법

**GitHub Actions**는 푸시 같은 일이 생기면 GitHub의 컴퓨터가 정해진 작업(테스트, 배포)을 자동으로 해 주는 기능이에요. 작업 내용은 `.github/workflows/*.yml`에 적어요.

| 워크플로 | 언제 | 하는 일 |
|---|---|---|
| **CI** (`ci.yml`) | `develop`, `feature/**`, `fix/**`, `chore/**`, `release/**`, `hotfix/**` 푸시, `main`·`develop` 대상 PR | 백엔드 테스트, 프론트 린트·빌드 |
| **Deploy** (`deploy.yml`) | `main` 푸시, 또는 수동 실행 | 위 테스트 → Docker 이미지 → 서버 전송 → `deploy.sh` |

둘 다 `*.md`, `docs/**`만 바뀐 푸시는 건너뛰어요(Deploy는 `scripts/**`도).

보는 법
1. 저장소 → **Actions** 탭 → 왼쪽에서 워크플로(CI / Deploy) 선택
2. 실행 목록에서 ✅(성공) / ❌(실패) / 🟡(진행 중) 확인
3. 실행을 누르고 → 작업(`test`, `deploy`) → 단계를 펼치면 로그가 보여요
4. 배포 실패라면 "서버에서 배포 스크립트 실행" 단계의 `❌` 줄과 `Caused by`를 먼저 봐요
5. 수동 배포: Deploy 워크플로 → **Run workflow** (`workflow_dispatch`)

## 7. 브랜치 보호

특정 브랜치(`main`, `develop`)에 **force push, 삭제, 테스트 실패한 코드 병합**을 막는 GitHub 설정이에요. 저장소 파일이 아니라 **GitHub 설정**이라서 Admin이 화면에서 켜야 해요.

위치: **Settings → Branches → Add branch protection rule** (또는 **Settings → Rules → Rulesets**)

추천 설정과 주의점은 [Git 가이드 12장](git-브랜치와-버전관리.md#12-pr-템플릿과-브랜치-보호)에 정리했어요. 요약하면 `main`·`develop`에 **force push 금지, 삭제 금지, 상태 검사(`test`) 통과 필수**를 켜고, "PR 필수"는 지금 작업 방식(로컬 병합 후 푸시)과 충돌하니 선택해서 켜요.

> 이 설정이 지금 켜져 있는지는 이 저장소 파일로 확인할 수 없어요. 저장소 주인이 Settings에서 확인해 주세요.

## 8. Issues와 Projects

| 기능 | 무엇 | 비유 |
|---|---|---|
| **Issues** | 할 일·버그·아이디어를 한 장씩 적는 카드. 번호(`#12`)가 붙고 댓글로 논의해요 | 포스트잇 한 장 |
| **Projects** | 이슈·PR을 칸반 보드(할 일 → 진행 중 → 완료)나 표로 모아 보는 화면. 조직 단위로도 만들 수 있어요 | 포스트잇을 붙이는 화이트보드 |
| Milestones | 이슈를 목표(예: `v1.2.0`)별로 묶기 | 마감일 있는 묶음 |

이 수업에서는 **GitHub Projects**로 진행 상황을 관리해요. 이슈를 만들고 Projects 보드에 올려 상태를 옮기면, 강사님이 조직 차원에서 진행을 볼 수 있어요.

연결 팁
- 커밋 메시지나 PR 본문에 `#12`를 쓰면 이슈에 링크가 걸려요.
- PR 본문에 `Closes #12`라고 쓰면 PR이 **기본 브랜치**에 병합될 때 이슈가 자동으로 닫혀요. 이 저장소의 기본 브랜치는 `main`이라서, `develop`에 병합하는 PR에서는 자동으로 닫히지 않을 수 있어요 (그땐 직접 닫아요).

> 이 저장소 안에는 이슈 템플릿(`.github/ISSUE_TEMPLATE/`)이 없고, PR 템플릿만 있어요.

## 9. 협업자 추가하기

| 방법 | 위치 | 필요한 권한 |
|---|---|---|
| 저장소에 사람 추가 | 저장소 **Settings → Collaborators and teams → Add people** | 저장소 Admin |
| 조직의 팀에 저장소 권한 주기 | 같은 화면 **Add teams** | 저장소 Admin + 팀이 있어야 함 |
| 조직 멤버로 초대 | `github.com/orgs/AIP-1/people` → Invite member | 조직 **Owner** |

- 초대받은 사람은 메일이나 GitHub 알림에서 **수락**해야 권한이 생겨요.
- 코드 리뷰만 받을 거라면 **Read**, 같이 푸시할 거라면 **Write**를 줘요. Admin은 꼭 필요한 사람에게만 줘요 (Secrets를 바꾸고 저장소를 지울 수 있어요).
- 조직 설정에 따라 학생이 외부 사람을 초대하지 못할 수 있어요. 그때는 강사님께 요청해요.

## 10. 좋은 README란

README는 저장소의 **첫 화면**이에요. GitHub에서 저장소를 열면 파일 목록 아래에 바로 보여요. 처음 온 사람(면접관, 협업자, 몇 달 뒤의 나)이 **3분 안에** 다음 질문에 답을 얻을 수 있어야 해요.

| 질문 | README의 답 |
|---|---|
| 이게 뭐예요? | 한 줄 소개, 서비스 주소 |
| 뭐가 특별해요? | 핵심 기능, 독창 기능 |
| 무엇으로 만들었어요? | 기술 스택 |
| 내 컴퓨터에서 어떻게 돌려요? | 준비물, 실행 명령어 (복사해서 바로 되게) |
| 잘 동작하는 걸 어떻게 믿어요? | 테스트 방법, 결과 |
| 더 알고 싶으면? | 상세 문서 링크 |

원칙
- **위에서 아래로 중요한 순서**: 소개 → 기능 → 실행 → 깊은 내용.
- **명령어는 복사해서 바로 실행되게**: 코드 블록에 넣고, 바꿔야 할 값은 따로 표시해요.
- **자세한 내용은 링크로**: README에 다 쓰면 길어서 안 읽어요. 설계·API·트러블슈팅은 `docs/`로 빼고 링크해요.
- **코드와 함께 갱신**: 실행 방법이 바뀌었는데 README가 그대로면 오히려 해가 돼요. 이 프로젝트는 완료 기준(CLAUDE.md 7장)에 "문서 동기화"가 있어요.

| 10 | 앞으로의 계획 (2차 개발) | 우선순위·영역·내용·"지금 준비된 것" 표 | 한계를 인정하고 다음 단계를 보여 줘요 |

잘된 점
- 차별점(기록 유니버스)이 첫 화면에 나와요.
- 실행·테스트·시연 데이터 명령이 모두 복사 가능한 코드 블록이에요.
- Secrets는 이름만 있고 값은 없어요.
- "앞으로의 계획"에 **"지금 준비된 것"** 열이 있어서, 계획이 막연한 희망이 아니라 현재 구조에서 이어진다는 걸 보여 줘요.

더 좋아질 수 있는 점 (선택)
- **스크린샷/GIF가 없어요.** 기록 우주·타임캡슐처럼 눈에 보이는 기능은 그림 한 장이 설명보다 강해요.
- 테스트 개수(백엔드 193개, 화면 점검 125개) 같은 숫자는 코드가 바뀌면 낡아요. 릴리스 때 다시 세어 갱신하거나 표현을 바꿔요.
- 라이선스, 만든 사람·연락처 절이 없어요. 포트폴리오로 쓸 거라면 맨 아래에 작성자 정보를 넣으면 좋아요.
- 일부 표현은 코드와 어긋나지 않는지 확인이 필요해요. 예: "앞으로의 계획" 5번의 "글 삭제 후 파일 삭제 이벤트"는 현재 이벤트 구조만 있고 글 삭제에는 연결되지 않았어요 ([파일 업로드 가이드 7장](파일-업로드.md#7-파일-지우기)).

### 배지(badge)는 선택이에요
README 맨 위의 작은 그림 버튼(예: CI 통과 여부, 버전)이에요. 있으면 상태가 한눈에 보이지만, 없어도 괜찮아요. 이 README에는 지금 배지가 없어요. 넣는다면 GitHub Actions가 제공하는 상태 배지가 가장 쉬워요.

비공개(Private) 저장소라면 배지 그림이 외부에서 보이지 않을 수 있어요.

## 13. FAQ

**Q. Settings 탭이 안 보여요.**
저장소에 Admin 권한이 없는 거예요. Secrets·브랜치 보호·협업자 초대는 Admin만 할 수 있어서 조직 Owner(강사님)께 요청해야 해요.

**Q. Secret 값을 잊어버렸어요. 어디서 봐요?**
GitHub은 저장한 값을 다시 보여 주지 않아요. 원래 값을 알고 있는 곳(서버 계정 정보, 수업 안내)에서 다시 확인해 **덮어써요.**

**Q. Secret을 바꿨는데 배포에 반영이 안 돼요.**
Secret은 워크플로가 **실행될 때** 읽어요. 바꾼 뒤 Actions에서 Deploy를 **Run workflow**로 다시 실행해요.

**Q. 내 개인 계정으로 저장소를 옮기고 싶어요 (포트폴리오).**
조직 저장소를 옮기는 것(Transfer)은 Admin 권한과 조직 정책이 필요해요. 보통은 옮기지 않고 **Fork**하거나, 새 개인 저장소를 만들어 `git push`로 이력을 복사해요. 이때 Secrets와 Actions 설정은 따라오지 않아요.

**Q. README에 서버 주소나 계정을 적어도 되나요?**
서비스 주소(`https://ownlog.java21.net`)와 **시연용 공개 계정**(`ownlog1234` 같은 시연 비밀번호)은 일부러 공개한 값이라 괜찮아요. 서버 SSH 정보, DB 비밀번호, JWT 비밀키는 절대 안 돼요.
