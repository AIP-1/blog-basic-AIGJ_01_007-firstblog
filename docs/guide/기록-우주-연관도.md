# 기록 우주 연관도: "정말 관련 있는 글"만 선으로 잇기

> 대상: 이 기능을 직접 만들지 않은 사람(벡터, TF-IDF가 처음인 사람)도 읽고 설명하고 고칠 수 있게 썼어요.
> 코드: `backend/src/main/java/com/ownlog/universe/service/Relatedness.java`(계산), `GraphService.java`(기준값, 연결),
> 테스트: `backend/src/test/java/com/ownlog/universe/RelatednessTest.java`(계산·측정), `GraphApiTest.java`(API·권한)

---

## 1. 무엇이 문제였나요

기록 우주(14.1 블로그 우주, 14.3 서비스 전체 우주)의 선은 두 가지였어요.

| 선 | 뜻 | 바꿨나요 |
|---|---|---|
| `LINK` (밝은 실선, 화살표) | 글쓴이가 직접 쓴 `[[링크]]` | 그대로 |
| `TAG` (흐린 점선) | **태그를 하나라도** 같이 쓰면 무조건 연결 | `RELATED`로 바꿨어요 |

여행 블로그라면 거의 모든 글에 `#여행`이 붙어요. 그러면 "부산 해운대"와 "도쿄 3박 4일"이 `#여행` 하나 때문에 이어지고,
글 N개가 모두 서로 이어져서 선이 N×(N−1)/2개, 거미줄이 돼요. 선이 "관련 있다"는 뜻을 잃은 거예요(무결성 문제).

주인이 물어본 것: **"벡터를 써서 관련도를 판단하면 어때요?"** → 네, 벡터를 써요. 다만 외부 AI가 아니라 **앱 안에서 계산하는 TF-IDF 벡터**를 골랐어요. 아래에서 왜 그런지 차근차근 설명해요.

## 2. 개념 먼저: 벡터, TF-IDF, 코사인 유사도

### 2.1 벡터 = "단어 → 숫자" 목록

컴퓨터는 글의 뜻을 바로 비교하지 못해요. 그래서 글을 **숫자 묶음(벡터)** 으로 바꿔요.
가장 쉬운 방법: 세상의 모든 단어를 칸으로 두고, 그 글에 나온 단어 칸에 숫자를 적는 거예요.

```
              부산  여행  맛집  지도  제주  일기
A "부산 여행 맛집"  1     1     1     0     0     0
B "부산 맛집 지도"  1     0     1     1     0     0
C "제주 여행 일기"  0     1     0     0     1     1
```

대부분의 칸이 0이라서 **0이 아닌 칸만 저장**해요(희소 벡터, sparse vector). 코드에서는 `Map<String, Double>`이에요.

### 2.2 TF-IDF = 단어마다 "얼마나 중요한가" 무게

모든 단어가 똑같이 중요하지 않아요. "여행 블로그의 `여행`"은 어느 글에나 있어서 글을 구분해 주지 못해요.

- **TF** (Term Frequency, 단어 빈도): 그 글에 그 단어가 얼마나 나오나요? 많을수록 그 글의 주제에 가까워요.
  우리는 **제목·태그는 2배, 요약은 1배**로 세요 (제목과 태그가 주제를 가장 잘 요약하니까요).
- **IDF** (Inverse Document Frequency, 역문서 빈도): 그 단어가 **몇 개의 글**에 나오나요? 드물수록 커요.
  우리 식: `idf = ln((N + 1) / (df + 1)) + 1` (N: 글 수, df: 그 단어가 나온 글 수). "+1"들은 글이 2~3개뿐일 때 0이 되지 않게 부드럽게 만든 거예요.
- **TF-IDF = TF × IDF**: "이 글에 자주, 다른 글엔 드물게" 나오는 단어가 큰 숫자를 가져요.

위 예(N = 3)에서 IDF는:

| 단어 | 나온 글 수(df) | IDF |
|---|---|---|
| 부산, 여행, 맛집 | 2 | ln(4/3) + 1 = **1.288** |
| 지도, 제주, 일기 | 1 | ln(4/2) + 1 = **1.693** |

### 2.3 코사인 유사도 = 두 벡터가 "같은 방향"인가

두 글 벡터 A, B의 **코사인 유사도** = (A·B) ÷ (|A| × |B|)

- **A·B (내적)**: 두 글이 **함께 가진 단어**의 무게를 곱해서 더한 값
- **|A| (길이)**: 자기 무게들을 제곱해서 더한 뒤 루트. 긴 글이 무조건 유리해지지 않게 나눠 줘요
- 결과는 0(겹치는 단어 없음) ~ 1(단어 비율이 똑같음)

손으로 계산해 볼게요.

```
A = {부산 1.288, 여행 1.288, 맛집 1.288}            |A| = √(3 × 1.288²)            = 2.230
B = {부산 1.288, 맛집 1.288, 지도 1.693}            |B| = √(2 × 1.288² + 1.693²)  = 2.487
C = {여행 1.288, 제주 1.693, 일기 1.693}            |C| = √(1.288² + 2 × 1.693²)  = 2.719

A·B = 부산(1.288×1.288) + 맛집(1.288×1.288) = 3.317   →  cos(A,B) = 3.317 / (2.230×2.487) = 0.60
A·C = 여행(1.288×1.288)                   = 1.658   →  cos(A,C) = 1.658 / (2.230×2.719) = 0.27
B·C = 0 (겹치는 단어 없음)                          →  cos(B,C) = 0
```

"부산 여행 맛집"과 "부산 맛집 지도"(0.60)는 이어지고, `여행`만 같은 "제주 여행 일기"(0.27)는 기준 0.3에 못 미쳐서 이어지지 않아요.

### 2.4 한국어는 조사가 문제예요 → 2글자 조각(bigram)

영어는 띄어쓰기로 단어가 나뉘지만, 한국어는 `여행을`, `여행은`, `여행에서`처럼 **조사가 붙어서** 단어 그대로 비교하면 모두 다른 말이에요.
형태소 분석기(새 라이브러리)를 쓰지 않고, **한글 덩어리를 2글자씩 겹쳐 잘라요**.

```
여행을   → 여행, 행을
여행은   → 여행, 행은        ← "여행" 조각이 겹쳐서 같은 말로 잡혀요
해운대   → 해운, 운대
Spring에서 → spring (영문은 소문자 단어 그대로) + 에서(흔한 조사라 버림)
```

- 한 글자 낱말(`더`, `잘`, `책`)과 숫자만 있는 것(`19`, `2026`)은 버려요. 주제를 거의 말해 주지 않아요.
- `에서`, `해요`, `니다` 같은 흔한 어미·조사 조각은 작은 금지어 목록(`STOP`)으로 버려요. IDF도 어차피 낮게 만들어요.
- 단어 나누기 코드: `Relatedness.tokenize()`, 테스트: `RelatednessTest.tokenizeKorean()`

### 2.5 임베딩(embedding)과 벡터 DB(pgvector)는 뭔가요?

- **임베딩**: OpenAI·Voyage 같은 AI 모델이 글을 **뜻을 담은 숫자 768~3072개**로 바꿔 줘요. "강아지"와 "반려견"처럼 **단어가 달라도 뜻이 같으면** 가까워요. TF-IDF는 이걸 못 해요(글자가 겹쳐야 해요).
- **벡터 DB / pgvector**: 임베딩을 DB에 저장하고 "가장 가까운 글 K개"를 빨리 찾게 해 주는 PostgreSQL 확장이에요(`CREATE EXTENSION vector`).

## 3. 선택지 비교

| | (a) 태그 하나라도 같으면 (예전) | (b) IDF 가중 태그 유사도 | (c) TF-IDF 글자 벡터 + 코사인 (앱 안에서) | (d) AI 임베딩 (외부 API / pgvector) |
|---|---|---|---|---|
| 정확도 | 낮음: 흔한 태그로 다 이어짐 | 보통: 태그 없는 글은 못 이음 | 보통~좋음: 태그 + 제목·요약 단어 | 가장 좋음: 뜻까지 비교 |
| 한국어 | 태그만 봐서 문제없음 | 문제없음 | 2글자 조각으로 조사 문제 해결 | 모델이 처리 |
| 비용·키 | 없음 | 없음 | 없음 | API 요금, API 키 관리 필요 |
| 개인정보 | 문제없음 | 문제없음 | **서버 밖으로 안 나감** | 글을 외부 회사로 보내요. 비공개·봉인 글은 절대 보내면 안 돼서 별도 관리가 필요해요 |
| 공용 DB | 문제없음 | 문제없음 | 문제없음 | pgvector는 확장 설치 권한이 필요해요. 수업 공용 PostgreSQL은 **설치할 수 없고**, 있는지도 몰라요 |
| 속도 | SQL 1번 | 계산 수 ms | 500개 기준 약 0.05~0.1초 (측정) | 글 쓸 때마다 API 호출(수백 ms), 저장·재계산 관리 |
| 설명 가능성 | "같은 태그" | "드문 태그 X가 같아요" | "드문 태그 X, 함께 나온 단어 Y" | "AI가 가깝다고 했어요" (이유를 보여주기 어려움) |
| 새 라이브러리·DB 변경 | 없음 | 없음 | **없음** | SDK 또는 확장 + Flyway 마이그레이션 |

**고른 것: (b) + (c)를 합친 방식.** 점수 = `max(태그 점수, 글자 점수)`

- 마감(2026-10-14) 직전이라 새 라이브러리·DB 변경·외부 키 없이 지금 바로 안전하게 넣을 수 있어요.
- 볼 수 있는 글의 제목·요약·태그만 서버 메모리에서 계산해서 **비공개·봉인 글이 밖으로 나갈 길이 없어요**.
- 선마다 **근거(태그·단어)** 를 보여줄 수 있어서 "왜 이어졌어요?"에 답할 수 있어요.

## 4. 알고리즘 한 단계씩

요청이 올 때마다 그 우주에 있는 별(최대 300개 / 500개)로 계산해요. 캐시나 DB 저장은 없어요.

| 단계 | 하는 일 | 코드 (`Relatedness.compute`) |
|---|---|---|
| 0 | **볼 수 있는 글만** 넣어요 (`connectable`: 방문자에게 잠긴 캡슐 제외, 비공개 글은 애초에 별이 아님) | `GraphService.build()` |
| 1 | 글마다 제목(×2)·요약(×1)·태그(×2)를 단어로 나눠 TF를 세요 | `// 2-1` |
| 2 | 단어·태그마다 몇 개의 글에 나오는지(DF) 세요. **글이 4개 이상이면 절반 넘게 나오는 것은 버려요** | `// 2-2`, `MIN_NODES_FOR_COMMON_CUT = 4`, `COMMON_RATIO = 0.5` |
| 3 | TF × IDF로 글 벡터를 만들고 길이를 구해요. 단어 → 그 단어를 가진 글 목록(역색인)도 만들어요 | `// 2-3` |
| 4 | **함께 가진 단어만** 곱해서 더해요(역색인 덕분에 모든 쌍 × 모든 단어를 돌지 않아요) → 코사인 | `// 2-4` |
| 5 | 태그 점수: IDF로 무게를 준 자카드 = 함께 가진 태그 무게 ÷ 둘 중 하나라도 가진 태그 무게 | `// 2-5` |
| 6 | 점수 = max(코사인, 태그 점수). **0.3 이상**이고 `[[링크]]`로 이미 이어지지 않은 쌍만 후보 | `// 2-6` |
| 7 | 별마다 **가장 가까운 3개**까지만. 한쪽이라도 상대를 3개 안에 꼽으면 남겨요. 전체 상한 1,000 / 1,500개 | `// 2-7` |
| 8 | 근거: 함께 붙은 드문 태그(최대 5개), 함께 나온 단어(최대 3개, 조사를 뗀 공통 부분 "여행을"·"여행은" → "여행") | `// 2-8` |

**왜 max인가요?** 태그는 글쓴이가 직접 고른 주제라 하나만 강해도 충분해요. 그런데 태그가 없는 글도 많아서, 평균(가중합)을 내면 태그 없는 글은 늘 점수가 반으로 깎여요. 둘 중 강한 쪽을 쓰면 "태그로 관련" 또는 "내용으로 관련"을 모두 잡아요.

**왜 한쪽만 꼽아도 남기나요(합집합)?** 양쪽 모두 서로를 3개 안에 꼽아야 남기면(교집합), 인기 많은 글 주변의 작은 글이 쉽게 외톨이가 돼요. 합집합이어도 별마다 자기가 고른 선은 3개라 전체 선 수는 많아야 별 수 × 3이에요.

**왜 `[[링크]]` 쌍은 빼나요?** 이미 밝은 실선이 있는데 점선을 겹쳐 그리면 선 수만 늘고 보이지도 않아요. 한 관계는 선 하나로 보여줘요.

### 응답 모양 (`GraphResponse.Edge`)

```json
{ "source": 51, "target": 17, "type": "LINK" }
{ "source": 17, "target": 30, "type": "RELATED", "weight": 0.36, "tags": ["부산"], "keywords": ["여행", "해운대"] }
```

- `RELATED`는 방향이 없어서 늘 `source < target`(번호 순)이에요. `weight`는 관련도 0~1(소수 둘째 자리).
- 예전 `TAG`의 `weight`(공유 개수, 정수)는 없어졌어요. 이 API를 쓰는 곳은 우리 화면뿐이라 함께 고쳤어요.

### 화면 (`UniverseCanvas.jsx`)

- `LINK`: 밝은 실선 + 화살표(그대로)
- `RELATED`: 점선, `weight`가 클수록 진하고(투명도 0.15 + 0.45×w) 굵어요(0.6 + 1.2×w). 물리 배치에서도 관련도가 높을수록 더 가깝게 당겨요
- 별에 마우스를 올리면 `관련: #부산 · 해운대`처럼 근거를 최대 4개 보여줘요
- 범례: "같은 태그" → **"관련 있는 글"** (`UniversePage.jsx`, `GlobalUniversePage.jsx`, e2e `check-universe.mjs`도 함께)

## 5. 기준값 고르기와 조정 방법

값은 `GraphService`에 있어요.

| 상수 | 값 | 뜻 | 올리면 / 내리면 |
|---|---|---|---|
| `MIN_RELATED_SCORE` | 0.3 | 이보다 낮은 쌍은 선 없음 | 올리면 더 엄격(선 적음), 내리면 느슨 |
| `RELATED_TOP_K` | 3 | 별마다 가장 가까운 K개 | 올리면 촘촘, 내리면 깔끔 |
| `MAX_RELATED_EDGES` / `MAX_UNIVERSE_RELATED_EDGES` | 1,000 / 1,500 | 전체 상한 (안전장치) | 보통 손대지 않아요 |
| `Relatedness.MIN_NODES_FOR_COMMON_CUT` | 4 | 글이 이만큼 이상이면 흔한 단어·태그 제외 | |
| `Relatedness.COMMON_RATIO` | 0.5 | 절반 넘게 나오면 "흔하다" | 내리면 더 많이 버려요 |

**0.3인 이유**: 태그만 보면 "무게로 따져 태그의 1/3 이상이 겹친다"는 뜻이에요. 태그 2개짜리 두 글이 1개를 같이 쓰고 무게가 같으면 1/3 = 0.33으로 통과해요. 같이 쓴 태그가 나머지 태그보다 **흔하면**(무게가 작으면) 1/3 아래로 내려가서 빠져요. 시연 데이터의 "부산 여행 2일차 ~ 제주 한 달 살기"(`#여행`만 같음)가 0.298로 딱 빠지는 값이에요.

시연 데이터(서비스 전체 우주, 글 24개)에서 기준별 관련 선 수 (`RelatednessTest.demoDataBeforeAfter`에서 기준만 바꿔 측정):

| 기준 | 관련 선 | 들어오는 쌍 (점수) |
|---|---|---|
| 0.30 (현재) | 2 | 부산 2일차 ~ 부산식 돼지국밥 (0.36), JVM 메모리 구조 ~ Spring Boot 시작하기 (0.30) |
| 0.25 | 5 | + 2일차 ~ 제주(0.298, `#여행`만), 라멘 ~ 김치찌개(0.29, `#레시피`만), 부산 1일차 ~ 부산에서 먹은 것들(0.25) |
| 0.15 | 19 | `#여행`·`#Spring`·`#Java` 하나만 같은 쌍이 대부분 들어와요 (예전과 비슷해짐) |

**조정 방법**

1. `RelatednessTest.OPTIONS`와 `GraphService.MIN_RELATED_SCORE`를 함께 바꿔요(테스트는 같은 값을 써요).
2. `cd backend && ./gradlew test --tests 'com.ownlog.universe.RelatednessTest' -i`로 돌리면 `[연관도]` 줄에 선 목록과 점수·근거가 찍혀요.
3. 실제 데이터로 보려면 `GET /api/universe` 응답의 `edges[?type=RELATED]`의 `weight`와 `tags`·`keywords`를 보면 돼요.

## 6. 개인정보와 무결성

- **계산에 들어가는 글 = 보는 사람이 볼 수 있는 글**. 별 목록은 이미 공개 조건(`PostCardQueries.PUBLIC_CONDITION`, 블로그 우주는 같은 조건 + 주인이면 비공개 포함)으로 걸러져 있어요.
- 방문자에게 **잠긴 타임캡슐**은 `connectable`에서 빠져서 제목·요약·태그가 단어 통계(IDF)에조차 들어가지 않아요. 그래서 "캡슐에 X라는 단어가 있어서 다른 글의 점수가 달라지는" 간접 유출도 없어요. (`GraphApiTest.sealedCapsuleIsLonelyLockedStar`)
- 비공개 글은 방문자 우주에 별로도 없고 계산에도 없어요. (`privatePostsOnlyForOwner`, `universeRelatedAcrossBlogs`)
- 근거로 보여주는 단어는 **양쪽 글 모두에 있는** 단어라서, 볼 수 있는 글의 제목·요약에 이미 보이는 말이에요.
- 본문 전체(`content`)는 읽지 않고 저장된 150자 요약(`summary`)만 써요. 쿼리가 가볍고, 요약은 이미 카드에 공개되는 글자예요.
- 외부로 아무것도 보내지 않아요.

## 7. 한계와 언제 임베딩으로 넘어갈까요

- **뜻은 몰라요**: "강아지"와 "반려견", "Spring"과 "스프링"은 글자가 달라서 이어지지 않아요.
- **요약이 짧아요**: 150자라 본문 깊은 곳의 주제는 못 봐요. 시연 데이터처럼 글이 짧으면 선이 적게 나와요(대신 정확해요).
- **2글자 조각의 잡음**: "함수는"·"변수는"이 `수는`으로 겹치는 일이 있어요. IDF가 낮춰 주지만 근거 단어에 가끔 보여요.
- **한 글자 낱말**(`책`, `꿈`)은 버려요.
- **글마다 매번 계산**: 300~500개라 0.1초 안이지만, 수천 개 우주를 한 번에 보여주려면 캐시나 미리 계산이 필요해요.

**임베딩으로 넘어갈 때(2차 후보)**

1. 서버 DB에 pgvector를 쓸 수 있는지 먼저 확인해요(`SELECT * FROM pg_available_extensions WHERE name = 'vector'`). 안 되면 임베딩을 `real[]`로 저장하고 앱에서 코사인을 계산해도 돼요(500개면 충분히 빨라요).
2. **공개 글만** 임베딩해요. 비공개·봉인 캡슐은 외부 API로 보내지 않아요(개봉 시점에 만들어요).
3. 글을 저장·수정할 때 비동기로 만들고(Flyway로 열 추가), 점수는 지금 구조 그대로 `max(태그 점수, 임베딩 코사인)`로 바꾸면 돼요. 상위 K개·기준값·근거 태그는 그대로 써요.
4. 새 라이브러리·외부 키·DB 변경이 모두 들어가서, CLAUDE.md 규칙대로 **먼저 물어보고** 진행해요.

## 8. 트러블슈팅: "흔한 태그 하나로 우주가 거미줄이 돼요"

**상황**
기록 우주에서 `#여행`, `#Spring`처럼 흔한 태그를 같이 쓴 글이 모두 점선으로 이어졌어요. 여행 블로그(공개 글 5개 중 4개에 `#여행`)는 8개 선이 생겨 사실상 모든 글이 이어졌고, 서비스 전체 우주에서는 태그 선이 링크 선보다 많아서 정말 관련 있는 연결이 묻혔어요.

**원인 분석**
- 예전 쿼리(`findTagEdges`)는 `post_tags`를 자기 자신과 조인해서 **태그를 1개 이상 공유하면** 선을 만들었어요. "그 태그가 얼마나 흔한지"를 전혀 보지 않았어요.
- 정렬도 "공유 개수"뿐이라, 태그를 1개씩만 쓰는 글끼리는 점수 차이가 없었어요.
- 선 수 상한(1,000 / 1,500)이 있어 화면은 버텼지만, 상한은 **어떤 선을 남길지**는 정해 주지 않아요. 별 500개 합성 데이터에서는 후보 쌍이 28,758개라 상한에서 잘린 1,500개가 거의 무작위였어요.

**해결**
- 쿼리 대신 앱에서 TF-IDF 벡터 + 코사인, IDF 가중 태그 자카드를 계산하고(`Relatedness`), 흔한 단어·태그 제외, 기준 0.3, 별마다 상위 3개로 걸렀어요.
- 새 선 종류 `RELATED`(관련도 `weight`, 근거 `tags`·`keywords`)를 만들고, `[[링크]]`와 겹치는 쌍은 뺐어요.
- 쓰지 않게 된 `findTagEdges` 쿼리와 `TagEdgeRow`는 지웠어요.

**결과** (시연 데이터 `scripts/seed-demo.mjs`의 공개 글을 그대로 옮긴 `RelatednessTest`에서 측정. 실제 서버 API가 아니라 같은 글로 계산한 값이에요)

| 우주 | 글 | 예전 태그 선 | 새 관련 선 | 링크 선 |
|---|---|---|---|---|
| 서비스 전체 우주 | 24 | **36** | **2** | 20 (그대로) |
| codewave (개발) | 10 | 16 | 1 | 그대로 |
| tripnote (여행) | 5 | 8 | 0 | 그대로 |
| cookbook (요리) | 3 | 3 | 0 | 그대로 |
| bookworm · runner | 2 · 4 | 1 · 1 | 0 · 0 | 그대로 |
| 합성 데이터 (별 500개, 넓은 태그 5종 + 좁은 태그 100종) | 500 | 28,758 (1,500에서 잘림) | 1,013 | – |

- 별 500개 계산 시간: 44~103ms (개발 PC, 테스트 실행 중 측정).
- 서비스 전체 우주의 선: 56개 → 22개. 남은 관련 선 2개는 "부산 2일차 ~ 부산식 돼지국밥"(`#부산`, 단어 `여행`·`일차`·`해운대`)처럼 사람이 봐도 납득되는 쌍이에요.
- 백엔드 테스트 179개 모두 통과 (연관도 단위 테스트 8개, 그래프 API 테스트 9개 포함).

**배운 점**
- "같은 것이 있다"와 "관련 있다"는 달라요. **얼마나 드문 것이 같은지**(IDF)를 봐야 관련도가 돼요.
- 상한(LIMIT)은 성능 안전장치일 뿐 품질 기준이 아니에요. 품질은 점수와 기준값으로 정하고, 상한은 그 뒤에 둬요.
- 벡터라고 꼭 AI 임베딩일 필요는 없어요. 데이터 규모(≤500)와 제약(외부 전송 금지, DB 확장 불가, 새 라이브러리 금지)에 맞으면 고전적인 TF-IDF가 더 안전하고 설명하기도 쉬워요.
- 기준값은 감으로 정하지 않고, 실제와 같은 데이터로 기준별 결과를 표로 뽑아 보고 정했어요(5장).
