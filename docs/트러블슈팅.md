# OwnLog 트러블슈팅 기록

> 2주 동안 OwnLog를 만들고 배포하면서 실제로 겪은 문제와 해결 과정이에요.
> 각 사례는 **상황 → 원인 분석 → 해결 → 결과 → 배운 점** 순서로 정리했어요. 코드와 테스트는 저장소에서 바로 확인할 수 있어요.

## 한눈에 보기

| # | 분야 | 문제 | 핵심 원인 | 해결 | 검증 |
|---|---|---|---|---|---|
| 1 | 배포·인프라 | 배포한 컨테이너가 DB에 연결되지 않음 | Docker 기본 네트워크에서 학교 내부망으로 가는 길이 막힘 | 배포 스크립트에 **스스로 원인을 찾는 진단** 추가 → `--network host` | 운영 배포 성공 |
| 2 | 보안 | `/%61pi/...`로 **로그인 없이 API 호출** | 인가 규칙은 디코딩 전 주소, MVC는 디코딩 후 주소로 판단 | 경로 패턴 매처로 통일 | 운영 서버 재현 → 401 확인 |
| 3 | 보안 | 프로필 사진 주소로 **남의 업로드 파일 삭제** | 파일 소유자를 기록하지 않음 | 지우기 전에 다른 곳에서 쓰는지 확인 | 회귀 테스트 |
| 4 | 보안 | 로그인 후 **외부 사이트로 이동** | 문자열 검사로는 브라우저의 URL 해석을 따라갈 수 없음 | URL로 해석해서 출처(origin) 비교 | 화면 점검 3가지 공격 주소 |
| 5 | 백엔드 | 한글 비밀번호 가입이 **500** | 글자 수와 바이트 수의 차이 (BCrypt 72바이트) | 바이트 길이 검증 어노테이션 | 회귀 테스트 |
| 6 | 동시성 | 조회수·좋아요가 **동시 요청에서 틀어질 위험** (설계 단계에서 차단) | JPA가 읽은 값으로 덮어쓰는 Lost Update | DB가 직접 더하기 + 엔티티 쓰기 차단 | 동시 100명 테스트 |
| 7 | 설계 | 기능이 늘수록 **비공개 글이 새는 경로**가 늘어남 | 공개 조건이 조회마다 흩어짐 | 공개 판단을 **두 곳**으로 모음 | 목록·검색·링크·그래프별 누수 테스트 |
| 8 | 데이터 | 글 요약에 `[[17\|제목]]` 문법이 그대로 노출 | 새 문법을 요약 규칙이 모름 + 이미 저장된 데이터 | 규칙 수정 + **데이터 마이그레이션** | 운영 0건 확인 |
| 9 | 프론트엔드 | 토큰이 만료되면 **공개 화면에서도** 로그인 화면으로 튕김 | 전역 401 처리가 세션 복원 요청까지 잡음 | 요청별 예외 옵션 | 화면 점검 |
| 10 | 프론트엔드 | "두 번 클릭 방지"를 넣었는데 **여전히 두 번 등록** | React state는 다음 렌더링에 바뀜 | 즉시 바뀌는 ref로 확인 | 화면 점검이 실패를 잡아냄 |
| 11 | 성능 | 타임랩스 재생 중 **페이지 전체가 초당 60번 다시 그려짐** | 애니메이션 값을 React state로 전달 | 캔버스에 직접 전달(imperative handle) | 계산량 O(E·N) → 0 |
| 12 | 테스트 | 화면 점검 결과가 **실행할 때마다 달라짐** | 브라우저 프로필을 공유해 이전 로그인 정보가 남음 | 실행마다 새 프로필 + 별도 DB 스키마 | 113개 안정적으로 통과 |

## 1. 배포한 컨테이너가 학교 내부망 DB에 연결되지 않음

**분야** 배포·인프라 · **영향** 서비스 배포 불가 · **관련 파일** `deploy/deploy.sh`

### 상황
GitHub Actions로 이미지를 만들어 수업 서버에 배포했는데, 컨테이너가 매번 90초 안에 뜨지 않았어요. 로그에는 이것만 남아 있었어요.
```
Caused by: java.net.SocketTimeoutException: Connect timed out
```
처음에는 DB 포트 값(GitHub Secret)이 틀렸다고 보고 고쳤지만, **같은 오류가 그대로** 났어요.

### 원인 분석
"비밀번호가 틀림"이면 `authentication failed`가 나와야 해요. "연결 시간 초과"는 **네트워크 경로** 문제라는 신호였어요. 가능한 원인이 세 가지라서, 추측을 멈추고 **배포 스크립트가 직접 확인하게** 바꿨어요.

1. 값 형식 오류 (공백, `http://`, `:포트`가 섞임)
2. 서버에서 DB까지 닿지 않음 (외부 주소·내부 주소 혼동)
3. 서버에서는 닿지만 컨테이너에서는 닿지 않음

```bash
# deploy.sh (요약): 앱을 띄우기 전에 서버와 컨테이너 양쪽에서 DB로 TCP 연결을 시험해요
echo "  DB 주소의 IP: $(getent hosts "$DB_ADDRESS" | awk '{print $1}')"
host_result=$(bash -c "$tcp_check")
container_result=$(docker run --rm -e DB_ADDRESS -e DB_PORT --entrypoint bash "$IMAGE" -c "$tcp_check")
```
다음 배포에서 결과가 바로 나왔어요.
```
DB 주소의 IP: 10.116.64.13        ← 학교 내부망
서버 → DB: OK / 컨테이너 → DB: FAIL
```
**값은 맞았고, Docker 기본 브리지 네트워크에서 학교 내부망으로 가는 경로가 막혀 있던 것**이었어요.

### 해결
컨테이너를 서버 네트워크로 실행하고(`--network host`), 포트 연결(`-p`) 대신 앱이 배정받은 포트로 직접 뜨게 했어요.
```bash
docker run -d --name ownlog --network host -e SERVER_PORT="$APP_PORT" ...
```

### 결과
- 배포에 성공했어요. 진단 단계는 그대로 남겨서, 이후 배포도 실패하면 **원인 메시지와 함께 90초를 기다리지 않고 바로** 멈춰요.
- 값 형식 오류는 `❌ DB_PORT가 숫자만으로 되어 있지 않아요`처럼 Secret 이름만 알려줘요. 값은 노출하지 않아요.

### 배운 점
원격 환경의 문제는 **추측으로 값을 바꾸기보다, 실패 지점을 나눠 확인하는 진단을 자동화**하는 게 빨랐어요. 같은 오류가 두 번 나면 접근 방식을 바꿔야 한다는 신호로 받아들여요.

## 2. 인코딩한 주소로 로그인 검사를 건너뜀 (인증 우회)

**분야** 보안 · **심각도** 높음 · **관련 파일** `global/config/SecurityConfig.java`

### 상황
마감 전 전체 코드 점검에서 발견했어요. `GET /api/users/me`는 토큰이 없으면 401인데, `GET /%61pi/users/me`(`%61` = `a`)는 **컨트롤러까지 들어가 500**이 났어요. 운영 서버에서도 같았고, 같은 방법으로 **로그인 없이 이미지 업로드**도 됐어요.

### 원인 분석
React 화면 주소(`/@아이디` 등)를 모두 열어 두려고 이런 규칙을 썼어요.
```java
.requestMatchers(request -> !request.getRequestURI().startsWith("/api/")).permitAll()
```
- `getRequestURI()`는 **디코딩하지 않은 원래 주소**(`/%61pi/images`)라 `/api/`로 시작하지 않아요 → **누구나 허용**
- Spring MVC는 **디코딩한 주소**(`/api/images`)로 컨트롤러를 찾아요 → 업로드 컨트롤러 실행

**인가 규칙과 라우팅이 같은 요청을 서로 다르게 해석**한 게 원인이었어요.

### 해결
MVC와 같은 방식으로 주소를 해석하는 경로 패턴 매처로 바꿨어요.
```java
.requestMatchers("/api/**").authenticated()   // 디코딩한 경로로 비교해요
.anyRequest().permitAll()                       // 화면 주소
```

### 결과
- 운영에서 `/%61pi/users/me` → **401** 확인
- 회귀 테스트: MockMvc가 주소를 다시 인코딩하지 않도록 `URI.create("/%61pi/users/me")`로 원래 주소를 그대로 보내서 검증해요 (`SecurityAuditTest`)

### 배운 점
보안 규칙은 **실제로 요청을 처리하는 계층과 같은 해석 기준**을 써야 해요. 람다로 직접 주소를 비교하는 건 편하지만, 프레임워크가 이미 맞춰 둔 정규화(디코딩, 경로 정리)를 건너뛰어요.

## 3. 프로필 사진 주소로 남의 업로드 파일을 지울 수 있음

**분야** 보안(IDOR) · **심각도** 높음 · **관련 파일** `user/service/UserService.java`, `global/storage/ImageReferenceChecker.java`

### 상황
프로필 사진을 바꾸거나 탈퇴하면 예전 사진 파일을 지워요. 그런데 프로필 사진 주소는 `/uploads/...` 형식인지만 검사했어요. 그래서 **남의 글에 있는 이미지 주소를 내 프로필로 저장했다가 바꾸면, 남의 파일이 지워져** 그 사람 글의 이미지가 깨졌어요.

### 원인 분석
업로드할 때 **누가 올렸는지 기록하지 않아서**, "이 파일을 지워도 되는가"를 판단할 근거가 없었어요.

### 해결 (선택지와 판단)
| 선택지 | 장점 | 단점 |
|---|---|---|
| 업로드 테이블(`uploads(url, user_id)`)로 소유자 기록 | 가장 정확해요 | 새 테이블·마이그레이션, 기존 파일 이관 필요 |
| **지우기 전에 다른 곳에서 쓰는지 확인** | 마이그레이션 없이 바로 막아요 | 삭제할 때 조회 1번 추가 |
| 파일을 아예 지우지 않기 | 가장 단순해요 | 쓰이지 않는 파일이 쌓여요 |

마감 직전이라 **두 번째**를 골랐어요. 다른 회원의 프로필이나 글(썸네일·본문)이 쓰고 있으면 지우지 않아요. 소유자 기록은 2차 계획에 넣었어요.
```java
private void deleteImageIfUnused(String url, Long userId) {
    if (!imageReferenceChecker.isUsedElsewhere(url, userId)) {
        eventPublisher.publishEvent(new ImageDeleteEvent(url));   // 커밋 후 삭제 (롤백되면 파일도 그대로)
    }
}
```

### 결과
- 회귀 테스트 2개: 남의 파일은 남고, 아무도 쓰지 않는 내 사진은 기존처럼 지워져요.
- 파일 삭제는 원래부터 `@TransactionalEventListener(AFTER_COMMIT)`로 DB가 확정된 뒤에만 해서, DB 롤백 때 이미지만 사라지는 일은 없었어요.

### 배운 점
"삭제"처럼 되돌릴 수 없는 동작은 **요청한 사람이 그 대상의 주인인지**를 먼저 따져야 해요. 완벽한 해결과 지금 할 수 있는 안전한 해결을 나눠서, 일정 안에서 위험부터 막았어요.

## 4. 로그인 후 외부 사이트로 보내지는 오픈 리다이렉트

**분야** 보안 · **관련 파일** `frontend/src/pages/LoginPage.jsx`

### 상황
로그인 화면은 `?redirect=/write`처럼 원래 보던 주소로 돌려보내요. `//evil.com`은 막고 있었는데, `?redirect=%2F%09%2Fevil.com`(`/` + **탭** + `/evil.com`)으로 로그인하면 **외부 사이트로 이동**했어요.

### 원인 분석
- 검사: `"/\t/evil.com"`은 `/`로 시작하고 `//`로 시작하지 않아서 통과해요.
- 브라우저: URL 표준에 따라 **탭·줄바꿈을 지우고** `//evil.com`으로 해석해요.
- 라우터: 다른 출처라 `history.pushState`가 실패하자 `location.assign`으로 이동해요.

**문자열 검사로는 브라우저의 URL 해석 규칙을 따라갈 수 없다**는 게 핵심이었어요.

### 해결
브라우저와 같은 방식으로 **URL로 해석한 뒤 출처를 비교**하고, 경로 부분만 써요. 제어 문자와 역슬래시는 먼저 거부해요.
```js
const url = new URL(redirect, window.location.origin)
return url.origin === window.location.origin ? url.pathname + url.search + url.hash : '/'
```

### 결과
화면 점검에서 `/%09/evil.example`, `/\evil.example`, `//evil.example` 세 가지 모두 우리 사이트에 머무는 걸 확인해요 (`e2e/check-audit`).

### 배운 점
보안 검증은 **해석 결과를 비교**해야 해요. 입력 모양을 막는 방식(블랙리스트)은 표준의 예외 규칙 하나에 무너져요.

## 5. 한글이 섞인 긴 비밀번호로 가입하면 500

**분야** 백엔드 · **관련 파일** `global/validation/MaxUtf8Bytes.java`

### 상황
비밀번호 규칙은 "8~64자, 영문·숫자 포함"이에요. 그런데 `a1` + 한글 30자(32자)로 가입하면 400이 아니라 **500**이 났어요.

### 원인 분석
BCrypt는 **72바이트**까지만 받아서, 넘으면 Spring Security 7이 예외를 던져요. 규칙은 **글자 수**를 셌지만, 한글은 UTF-8에서 한 글자가 3바이트라 32자가 **92바이트**였어요.

### 해결
바이트 길이를 검사하는 검증 어노테이션을 만들어 가입·비밀번호 변경 요청에 붙였어요. 다른 입력 오류와 똑같이 **어느 칸이 왜 틀렸는지**(`fieldErrors`) 알려줘요.
```java
@Pattern(regexp = PasswordPolicy.REGEX, message = PasswordPolicy.MESSAGE)
@MaxUtf8Bytes(value = PasswordPolicy.MAX_BYTES, message = PasswordPolicy.BYTES_MESSAGE)   // 72
String password,
```

### 결과
92바이트는 400, 72바이트 이하의 한글 비밀번호는 그대로 가입돼요 (`SecurityAuditTest`). 요구사항의 입력 규칙에도 반영했어요.

### 배운 점
길이 제한은 **어느 단위(글자·바이트)로 세는지**까지 정해야 해요. 라이브러리의 한계는 입력 검증 단계에서 사용자에게 설명할 수 있는 규칙으로 바꿔야 500이 사라져요.

## 6. 조회수·좋아요가 동시 요청에서 틀어질 위험 (Lost Update)

**분야** 동시성 · **관련 파일** `post/domain/Post.java`, `post/repository/PostRepository.java`

### 상황
백엔드를 설계할 때, 조회수·좋아요를 엔티티 필드로 더하는 흔한 방식으로는 여러 명이 동시에 같은 글을 보거나 좋아요를 누르면 숫자가 실제보다 적게 저장된다는 걸 확인했어요. **사고가 나기 전에 구조로 막고, 동시성 테스트로 증명한 사례**예요.

### 원인 분석
엔티티 값을 바꿔 저장하는 방식(`post.setViewCount(post.getViewCount() + 1)`)은 **읽은 값 + 1**을 저장해요. 두 요청이 같은 값(10)을 읽으면 둘 다 11을 저장해서 하나가 사라져요. 게다가 Hibernate는 수정할 때 **모든 컬럼을 UPDATE**해서, 다른 필드(예: 제목)를 고친 요청도 예전 조회수로 덮어쓸 수 있었어요.

### 해결
- 카운터는 **DB가 직접 더해요**: `UPDATE posts SET view_count = view_count + 1 WHERE id = ?`
- 엔티티의 카운터 필드는 `insertable = false, updatable = false`로 막아서, 엔티티 저장이 카운터를 덮어쓰지 못해요.
- 좋아요 중복은 PK(회원, 글)와 `INSERT ... ON CONFLICT DO NOTHING`으로 막고, **실제로 들어간 행이 1개일 때만** 좋아요 수를 올려요.

### 결과
| 테스트 | 결과 |
|---|---|
| 서로 다른 회원 100명이 동시에 좋아요 | 정확히 100 |
| 한 회원이 동시에 10번 연타 | 정확히 1 |
| 방문자 50명이 동시에 조회 | 정확히 50 |

### 배운 점
"읽고 → 계산하고 → 쓰는" 코드는 동시에 실행되면 깨져요. 숫자 세기는 **DB의 원자적 연산**에 맡기고, 중복 방지는 **DB 제약**으로 보장하는 게 가장 확실했어요.

## 7. 기능이 늘수록 비공개 글이 새는 경로도 늘어남

**분야** 설계 · **관련 파일** `post/repository/PostCardQueries.java`, `post/domain/Post.java`

### 상황
글을 볼 수 있는 조건은 "발행 + 글 공개 + 카테고리 공개"예요. 그런데 이 조건을 쓰는 곳이 메인, 검색, 태그, 토픽, 인기, 블로그 목록, 북마크, 사이드바 글 수, 그리고 나중에 추가한 백링크, 기록 우주, 잔디까지 계속 늘었어요. **한 곳만 빠뜨려도 비공개 글이 새요.** 타임캡슐(정한 시각까지 봉인)을 추가할 때는 이 조건 자체가 바뀌어야 했어요.

### 해결
공개 판단을 **딱 두 곳**에만 뒀어요.
- 목록 쿼리(JPQL): `PostCardQueries.PUBLIC_CONDITION` 상수 하나를 모든 목록이 조합해서 써요.
- 엔티티: `Post.isViewableBy(회원)` 하나를 상세, 댓글, 좋아요, 신고, 링크 대상이 함께 써요.

타임캡슐은 **새 컬럼 하나**(`sealed_at`)로 끝냈어요. 개봉 시각을 `published_at`에 넣고, 공개 조건에 **한 줄**만 더했어요.
```java
and p.publishedAt <= current_timestamp   // 봉인된 캡슐은 모든 목록에서 한 번에 빠져요
```
스케줄러 없이 시각이 지나면 저절로 공개되고, 최신순 정렬도 그대로 맞아요.

### 결과
- 타임캡슐을 추가하면서 고친 목록 쿼리는 **0개**예요. 상수 한 줄로 8개 목록에 한 번에 적용됐어요.
- "받는 사람 캡슐"(둘만 보는 편지)도 `isViewableBy`에 조건 하나를 더하는 것으로 댓글, 좋아요, 링크 대상까지 적용됐어요.
- 기능마다 "새는 경로" 테스트를 둬요. 비공개, 봉인, 받는 사람 캡슐이 목록, 검색, 태그, 링크 미리보기, 그래프, 잔디에 나오지 않는지 확인해요.

### 배운 점
보안 조건은 **기능 수만큼 복사되면 언젠가 하나가 빠져요.** 조건을 한 곳에 모으면 새 기능은 그 조건을 "재사용"만 하면 되고, 리뷰할 곳도 두 곳으로 줄어요.

## 8. 글 요약에 `[[17|제목]]` 문법이 그대로 노출

**분야** 데이터 · **관련 파일** `global/util/MarkdownText.java`, `db/migration/V5__clean_link_summaries.sql`

### 상황
글과 글을 잇는 `[[번호|표시 글자]]` 문법을 추가한 뒤, 카드 요약과 링크 미리보기에 `[[3|Spring Boot 시작하기]]`가 그대로 보였어요. 화면 점검 스크린샷을 검토하다 발견했어요.

### 원인 분석
요약은 **글을 저장할 때 한 번 만들어 DB에 넣어요**(목록이 본문을 읽지 않게 하려고). 그래서 두 가지를 고쳐야 했어요.
1. 요약 생성 규칙이 새 문법을 몰라요 → 앞으로 저장할 글
2. **이미 저장된 요약** → 운영 DB에 이미 들어간 데이터

### 해결
- 요약 규칙에서 `[[번호|글자]]`를 글자만 남겨요. **자르기(150자) 전에** 처리해요.
- 기존 데이터는 Flyway 데이터 마이그레이션(V5)으로 정리했어요. 검증 중에 요약이 링크 중간에서 잘린 경우(`…[[19|클린 코드를 읽…`)도 찾아서 함께 처리했어요.
```sql
UPDATE posts SET summary = regexp_replace(
         regexp_replace(summary, '\[\[[0-9]{1,18}\|([^]\n]{1,100})\]\]', '\1', 'g'),
         '\[\[[0-9]{1,18}\|', '', 'g')
 WHERE summary LIKE '%[[%';
```

### 결과
배포 후 운영 API에서 `[[`가 남은 요약 **0건**을 확인했어요.

### 배운 점
- **저장 시점에 만드는 파생 데이터**(요약, 썸네일)는 규칙을 바꾸면 기존 데이터도 같이 옮겨야 해요.
- 잘린 경우를 처리하려고 V5를 고칠 때, 로컬 DB에는 이미 V5가 적용돼 있었어요. Flyway는 적용된 파일이 바뀌면(체크섬 불일치) 서버를 띄우지 않아서, 로컬 적용 기록을 지우고 다시 적용했어요. V5가 아직 운영에 배포되기 전이라 가능했던 방법이에요. 그래서 **"배포된 마이그레이션은 절대 고치지 않고 새 버전을 만든다"**를 프로젝트 규칙(CLAUDE.md)으로 정했어요.

## 9. 토큰이 만료되면 공개 화면에서도 로그인 화면으로 튕김

**분야** 프론트엔드 · **관련 파일** `frontend/src/api/client.js`, `auth/AuthProvider.jsx`

### 상황
로그인 토큰은 2시간 뒤 만료돼요. 만료된 토큰이 남은 채로 사이트에 다시 들어오면, **메인이나 회원가입처럼 공개된 화면인데도** 로그인 화면으로 보내졌어요. 처음에는 화면 점검의 테스트 데이터 문제로 보였는데, 원인을 따라가 보니 실제 버그였어요.

### 원인 분석
axios 응답 인터셉터가 **모든 401**을 받으면 토큰을 지우고 로그인 화면으로 보내요. 그런데 새로고침 때 로그인 상태를 복원하는 `/users/me` 요청도 401이면 같은 처리를 받았어요. 이 요청은 "실패하면 조용히 비회원으로 보면 되는" 요청이었어요.

### 해결
- 요청마다 **로그인 화면으로 보내지 않을 수 있는 옵션**(`skipAuthRedirect`)을 두고, 세션 복원 요청에만 썼어요.
- 이후 점검에서 하나 더 고쳤어요. 네트워크 오류나 배포 중(502)일 때도 토큰을 지우고 있어서, **401일 때만** 지우게 했어요.
```js
api.get('/users/me', { skipAuthRedirect: true })
   .catch((err) => err.response?.status === 401 && tokenStorage.clear())
```

### 결과
잘못된 토큰으로 `/`, `/signup`, `/login`에 들어가도 그 화면에 그대로 있고 토큰만 지워지는 걸 화면 점검으로 확인해요 (`e2e/check-expired`).

### 배운 점
전역 에러 처리는 편하지만 **요청의 의도**(꼭 필요한 요청인지, 실패해도 되는 요청인지)를 모르면 과하게 동작해요. 예외를 둘 수 있는 길을 처음부터 열어 두는 게 좋아요.

## 10. 두 번 클릭 방지를 넣었는데 여전히 댓글이 두 번 등록됨

**분야** 프론트엔드(React) · **관련 파일** `frontend/src/components/CommentSection.jsx`

### 상황
점검에서 "댓글 등록을 두 번 누르면 두 개 생긴다"를 발견해 `sending` state로 막았어요. 그런데 **화면 점검이 `0 → 2`로 실패**했어요. 수정이 통하지 않은 거예요.

### 원인 분석
```js
if (sending) return
setSending(true)   // 이 값은 다음 렌더링부터 보여요
```
React state는 **다음 렌더링에** 바뀌어요. 같은 순간에 두 번 클릭하면 두 이벤트 모두 `sending === false`인 같은 렌더링의 값을 봐서 둘 다 통과해요.

### 해결
값을 **즉시** 바꾸는 `useRef`로 확인하고, state는 버튼 비활성화 표시에만 써요.
```js
if (sendingRef.current) return
sendingRef.current = true
setSending(true)   // 화면 표시용
```

### 결과
같은 순간 두 번 클릭해도 댓글이 1개만 생겨요 (`e2e/check-audit`). 신고 창에도 같은 수정을 적용했어요.

### 배운 점
- **화면 표시용 상태와 즉시 판단용 값은 다르다**는 걸 다시 확인했어요.
- 무엇보다 **고쳤다고 생각한 수정을 자동 점검이 잡아냈어요.** 수정마다 회귀 점검을 함께 두는 이유예요.

## 11. 타임랩스 재생 중 페이지 전체가 초당 60번 다시 그려짐

**분야** 성능 · **관련 파일** `components/Timelapse.jsx`, `components/UniverseCanvas.jsx`

### 상황
기록 우주의 타임랩스(첫 기록부터 별이 하나씩 태어나는 애니메이션)를 재생하면, 매 프레임 바뀌는 날짜 값이 부모 페이지의 state를 거쳐 캔버스로 전달됐어요. 그래서 **페이지 전체가 초당 60번** 다시 그려졌어요. 서비스 전체 우주는 "블로그를 잇는 연결"을 셀 때 선마다 별 전체를 찾아서, **프레임마다 O(선 × 별)** 계산을 반복했어요.

### 해결
- 애니메이션 값은 React state가 아니라 **캔버스에 직접 전달**해요 (`useImperativeHandle`). 캔버스는 원래 자기 루프(requestAnimationFrame)로 그리고 있어서, 값만 바꿔 주면 돼요.
- 연결 수는 별 id → 블로그 지도(Map)를 한 번 만들어 계산하고 `useMemo`로 기억해요.
```jsx
<UniverseCanvas ref={canvasRef} ... />
<Timelapse onChange={(until) => canvasRef.current?.setUntil(until)} />
```

### 결과
재생 중 **페이지(부모 컴포넌트) 다시 그리기는 0회**가 됐어요. 다시 그려지는 건 타임랩스 막대 하나뿐이에요. 연결 수 계산은 **데이터가 바뀔 때 1회**로 줄었어요.

### 배운 점
React state는 "화면 구조가 바뀌는 값"에 쓰고, **애니메이션처럼 자주 바뀌는 값은 렌더링 밖으로** 빼는 게 맞아요.

## 12. 화면 점검 결과가 실행할 때마다 달라짐

**분야** 테스트 · **관련 파일** `e2e/cdp.mjs`, `e2e/README.md`

### 상황
헤드리스 Chrome으로 화면을 직접 눌러 보는 점검을 만들었는데, 같은 코드인데도 **가끔 로그인 화면으로 튕기며 실패**했어요.

### 원인 분석
모든 점검이 **브라우저 프로필 하나를 같이 써서**, 이전 점검의 로그인 토큰이 localStorage에 남았어요. 지운 뒤 확인해도 다음 실행에 토큰이 다시 나타났는데, Chrome을 바로 종료해서 localStorage 저장이 디스크에 늦게 반영된 것으로 보여요. 그 토큰의 주인이 이전 점검에서 탈퇴한 회원이면 401이 났어요. 이게 9번 버그를 발견한 계기이기도 했어요.

### 해결
- 실행마다 **임시 프로필로 새로 시작**하고, 끝나면 지워요.
- 점검이 실제로 가입·탈퇴를 해서 시연 데이터가 더러워지는 문제도 있었어요. 그래서 **배포와 같은 Docker 이미지를 별도 DB 스키마(`e2e`)로 띄워서** 돌리는 방법을 만들었어요. 시연 DB는 건드리지 않고, 운영과 같은 조건(화면과 API가 한 주소)에서 점검해요.

### 결과
113개 항목이 실행할 때마다 같은 결과를 내요. `node e2e/run-all.mjs` 한 줄로 누구나 다시 돌릴 수 있어요.

### 배운 점
불안정한 테스트는 테스트를 믿지 못하게 만들어요. **테스트끼리 상태를 공유하지 않게 격리**하는 것이 첫 번째였고, 격리하다 보니 실제 버그(9번)도 드러났어요.

## 문제를 대하는 방식 (정리)

1. **재현부터 해요.** 운영 서버의 인증 우회(2번)도 상태를 바꾸지 않는 GET 요청으로 먼저 재현하고 고쳤어요.
2. **추측 대신 진단을 자동화해요.** 같은 실패가 반복되면 값을 바꾸지 않고 확인 단계를 넣었어요(1번).
3. **위험한 조건은 한 곳에 모아요.** 공개 조건(7번), 파일 삭제 판단(3번)처럼 빠뜨리면 사고가 나는 규칙은 재사용하는 구조로 만들었어요.
4. **고친 것마다 회귀 테스트를 남겨요.** 백엔드 169개, 화면 점검 113개이고, 그중 하나는 제 수정이 틀렸다는 걸 잡아냈어요(10번).
5. **일정과 완성도 사이에서 선택한 이유를 기록해요.** 지금 막을 것과 2차로 미룬 것을 [점검 보고서](점검-보고서.md)와 README "앞으로의 계획"에 남겼어요.
