## 0. 요청 경로

```
브라우저 ──https──▶ 공용 Nginx :443 (강사님 관리, HTTPS 종료)
                       │ http
                       ▼
             [레포 설계] 우리 프록시 컨테이너 :8360 ─▶ blue :8361 / green :8362
             [현재 운영] ownlog 컨테이너 :8360 (v1.1.0, 단순 재시작)
                       ▼
                   PostgreSQL
```
- 화면(React)과 API(Spring)는 **같은 컨테이너, 같은 포트**에서 나온다 (Dockerfile).
- 레포 코드와 실제 서버가 다를 수 있다. 확인한 날 운영은 아직 v1.1.0이었다.

### ✍️ 내 말로
- 사용자와 웹서버 **Nginx** 간에는 안전하게 **HTTPS**로 통신한다.
- 하지만 Nginx(안내데스크 = **프록시**: 사용자와 앱 사이에서 요청을 대신 전달해 주는 대리인)와 **앱**(백엔드: 진짜 업무)은 내부에서 **HTTP**로 통신한다.
- 그래서 앱이 로그인 정보나 주소 생성을 정상적으로 처리하려면, Nginx가 정해 준 **"이거 원래 HTTPS 요청이었어"** 라는 메모(`X-Forwarded-Proto`)를 **신뢰하도록 앱 설정을 켜 두어야** 한다.

## 1. 리버스 프록시 눈으로 보기

| 명령 | 결과 |
|---|---|
| `curl -sI .../api/topics` (HEAD) | **401** |
| `curl -si .../api/topics` (GET) | **200** |

- `server: nginx/1.18.0` → 맨 바깥 프록시(공용 Nginx)가 보인다. Nginx는 뒤쪽의 `Server` 헤더를 자기 것으로 바꾸므로, **이 줄로는 몇 단인지 알 수 없다.**
- `x-frame-options: DENY` 같은 Spring Security 헤더 → 요청이 앱까지 갔다 왔다.
- `SecurityConfig`는 `/api/topics`를 **GET일 때만** 공개한다. 규칙은 위에서부터 비교하고, 처음 맞는 하나만 적용된다. HEAD는 아래의 `/api/**` 로그인 필요 규칙에 걸린다.
- 생각해 볼 것: HEAD로 살아 있는지 확인하는 모니터링 도구는 ownlog를 "이상"으로 오판할 수 있다.

### ✍️ 내 말로
- 내부를 감추기 위해 해당 API에서만 내부를 보여준다.
- HTTP 메서드가 달라지면 보안에 따라 달라진다.

> 📝 **짚을 점:** 첫 줄은 정확하지 않아요. 401은 "내부를 감추려고"가 아니라, 보안 규칙이 `/api/topics`를 **GET일 때만** 공개하도록 적혀 있어서 생겼어요. HEAD는 그 규칙에 맞지 않아 아래의 "로그인 필요" 규칙으로 떨어졌어요. 두 번째 줄이 핵심이고 맞아요.

## 4. X-Forwarded-Proto와 forward-headers-strategy

같은 요청 `curl -si -H "X-Forwarded-Proto: https" http://localhost:8081/api/topics`

| 설정 | HSTS 헤더 |
|---|---|
| 없음 (로컬 기본) | 없음 |
| `framework` | `max-age=31536000 ; includeSubDomains` |

- Spring Security는 요청이 https라고 **믿을 때만** HSTS를 붙인다.
- 운영 응답의 HSTS도 글자까지 같았다 (`;` 앞 공백까지). 그래서 공용 Nginx가 `X-Forwarded-Proto`를 넘겨 주고, 운영 설정이 동작한다고 **추정**했다.
- 설정 이름은 환경변수로도 줄 수 있다: `server.forward-headers-strategy` → `SERVER_FORWARD_HEADERS_STRATEGY`
- ⚠️ curl로 **직접 쓴 가짜 헤더**도 믿었다. 프록시를 거치지 않고 앱에 바로 닿을 수 있으면 위험하다 → 2단계

### ✍️ 내 말로
- (0단계와 같음) 앱이 로그인 정보나 주소 생성을 정상적으로 처리하려면, Nginx가 붙여 준 메모(`X-Forwarded-Proto`)를 신뢰하도록 앱 설정을 켜 두어야 한다.
- `forward-headers-strategy`는 **믿을지 말지의 스위치**다.
  - `framework`: 누가 보낸 헤더든 믿는다.
  - `native`: 내부망 IP에서 온 것만 믿는다.

> 📝 **짚을 점:** 대체로 맞아요. `native`는 웹 서버(Tomcat)의 기능을 쓰는데, "내부망 IP만 믿는다"는 건 **Tomcat의 기본 설정** 기준이에요(다른 서버나 설정에 따라 달라서 **확인 필요**). 그리고 `framework`가 "누구 헤더든 믿는다"는 점이 이번 실험에서 본 **위조 위험**이에요. 그래서 앱 포트를 프록시만 접근할 수 있게 막는 게(2단계) 함께 필요해요.

## 2. 포트 노출

| 확인 | 결과 |
|---|---|
| `lsof -iTCP -sTCP:LISTEN -P -n` | DB `*:5432` (Docker Desktop), Spring `*:8080` |
| 와이파이 IP로 8080 요청 | **200** (바깥에서 들어와짐) |
| 와이파이 IP로 5432 연결 | **열림** |

- `"5432:5432"`처럼 주소를 안 적으면 Docker는 0.0.0.0(전체)에 연다. Spring도 `server.address`가 없으면 전체에 연다.
- 고치기: `"127.0.0.1:5432:5432"` → 나만 접속. (아직 적용 안 함)
- 맥은 Docker Desktop이 포트를 대신 열고, 리눅스는 Docker가 iptables를 직접 고친다. "Docker가 UFW를 우회한다"는 리눅스에서 `-p`로 공개할 때 이야기다.
- 우리 서버는 `--network host`라 Docker가 방화벽 규칙을 고치지 않는다 → UFW가 그대로 적용된다. 실제로 막혀 있는지는 **확인 필요** (`ss -tlnp | grep 836`, `sudo ufw status`).

### ✍️ 내 말로
- 앞에 주소를 적지 않으면 누구나 다 들어올 수 있다.
- 그러면 우리의 포트가 노출될 가능성이 있다.
- 그래서 앞에 적어 주자. (예: `127.0.0.1:5432:5432`)

> 📝 **짚을 점:** "누구나"는 정확히는 **같은 네트워크(와이파이)에서 내 컴퓨터에 닿을 수 있는 누구나**예요. 서버라면 방화벽 설정에 따라 인터넷 전체가 될 수도 있어요.

## 7. 헬스 체크

401이 나는 `/api/users/me`로 실험

| 명령 | 종료 코드 | 배포에서는 |
|---|---|---|
| `curl -s` | 0 (성공) | 고장 난 새 버전으로도 전환해 버림 |
| `curl -fs` | 22 (실패) | 전환하지 않음 |

- curl은 택배 기사다. 답장이 오면 내용이 401·500이어도 배달 성공이다.
- 셸(`until`, `if`)은 상태 코드를 읽지 않고 **종료 코드만** 본다.
- `-f`는 "400 이상 = 실패"로 번역해 주는 통역사다.
- "몇 초 기다리기"는 앱이 떴는지 모른다. 헬스 체크는 **실제 응답을 확인한 뒤에만** 넘어간다.
- ownlog는 actuator 없이 `/api/topics`(DB에서 읽음)로 확인 → 200이면 앱과 DB 연결까지 확인된다.

### ✍️ 내 말로
- `-f` 설정을 넣지 않으면 **도착만 하면 오케이**라, 문제가 생겨도 오케이가 될 수 있다.

## 8. 무중단 배포 (블루-그린, `deploy/deploy.sh`)

```
1) 쉬는 쪽(green)에 새 버전
2) curl -fs 로 정상 확인        ← 7단계 (실패하면 green만 지우고 끝)
3) 프록시를 green으로 + nginx -s reload   ← 1단계
4) 10초 뒤 blue를 docker stop   ← 6단계
```
- 2)에서 `-f`가 빠지면 500을 내는 새 버전으로 전환되고, 사용자는 모두 500을 본다.
- 로컬 측정: 배포 중 요청 13,308건 실패 0, 예전 방식(끄고 켜기)은 308건 실패.

### ✍️ 내 말로
- 위의 7번에서 정리한 것과 동일하다.

> 📝 **짚을 점:** 7번(`-f`)은 8번의 **한 부품**이에요. 8번 전체는 "새 버전을 옆에 띄우고 → 정상인지 확인한 뒤에만 → 프록시를 바꾸고 → 예전 버전을 정상 종료"하는 흐름이라, 7번(확인)·1번(프록시)·6번(정상 종료)을 합친 거예요.

## 6. graceful shutdown

```
0초   docker stop → SIGTERM: Spring은 새 요청을 거절하고 처리 중인 요청은 계속 (최대 20초)
10초  -t 10 이면 → SIGKILL (무시할 수 없는 강제 종료) → 15초짜리 업로드는 끊김
```
- 순서: `docker stop -t` > Spring 대기(`timeout-per-shutdown-phase`) > 가장 긴 요청
- ownlog: 30초 > 20초

### ✍️ 내 말로
- **"마무리하고 나오세요"** 가 graceful shutdown이다.
- 그런데 여기서 `docker stop -t`는 바로 kill을 내 버린다.
- 그래서 도커가 더 대기가 길어야 한다.

> 📝 **짚을 점:** `docker stop -t`는 **바로** kill하지 않아요. 먼저 SIGTERM("마무리하고 나오세요")을 보내고, **`-t`초 동안 기다린 뒤에도** 안 꺼지면 그때 SIGKILL(강제 종료)을 보내요. 그래서 그 대기 시간이 Spring 대기보다 길어야 한다는 결론은 맞아요.

## 9·10. 개념

- **배포 동시 실행:** 둘 다 `active-color`를 blue로 읽고 둘 다 green을 띄워 서로 지울 수 있다. 막는 법은 `flock`(서버 잠금), Actions `concurrency:`(줄 세우기). ownlog에는 아직 없다.
- **expand-contract:** 배포 중에는 예전·새 버전이 같은 DB를 쓴다 → 컬럼은 추가만 하고 삭제는 다음 배포에서. (V6)
- **멱등성:** 같은 요청을 두 번 보내도 한 번과 같아야 한다. 좋아요는 `ON CONFLICT`.
- **ddl-auto:** `update`는 앱이 테이블을 바꾼다. ownlog는 `validate`(검사만), 바꾸는 건 Flyway만.

### ✍️ 내 말로
- **동시 실행:** 막기 위해서는 `flock`, Actions `concurrency` 정도가 있다.
- **expand-contract:** 같은 DB를 사용하는데 name과 nickname으로 분리하여 안전하게 배포한다.
- **멱등성:** 같은 요청을 두 번 보내도 한 번과 같아야 한다.
- **ddl-auto:** `update`는 전체 수정, `validate`는 검사, Flyway는 바꾸기만 하고 데이터는 유지.

> 📝 **짚을 점**
> - **expand-contract**는 "두 컬럼으로 분리"가 아니라 **순서**의 이야기예요. 예: `name`을 `nickname`으로 바꾸고 싶으면 ① `nickname`을 **추가**(expand)하고 새 코드는 둘 다 다룸 → ② 모든 서버가 새 버전이 된 **다음 배포에서** `name`을 **삭제**(contract). 한 번에 이름을 바꾸면 배포 중 아직 떠 있는 예전 버전이 깨져요.
> - **`update`** 는 "전체 수정"이라기보다, 앱이 뜰 때 엔티티에 맞춰 테이블을 **자동으로 고치는** 설정이에요(주로 추가, 삭제는 안 함). 위험한 이유는 **검토 없이** 운영 DB가 바뀌기 때문이에요.
> - **Flyway**는 내가 쓴 `V*.sql`을 **순서대로 한 번씩** 실행해요. 데이터가 유지되는 건 그 SQL이 지우지 않을 때만이에요.
