## A. 프로젝트와 기획

### 1. OwnLog를 1분 안에 소개해 주세요.
**답변 핵심**
- 누구나 가입해서 자기 블로그를 운영하는 **멀티유저 블로그 플랫폼**(티스토리형)이에요. 2주 동안 기획부터 배포까지 혼자 진행했어요.
- 기본 기능(글·댓글·좋아요·북마크·신고·검색·임시저장) 위에, **"기록이 시간과 연결로 자라는 블로그"**라는 독창 기능 **기록 유니버스**를 만들었어요: 정한 시각에 열리는 타임캡슐, `[[글]]` 연결과 백링크, 글을 별로 보여 주는 기록 우주, 기록 잔디.
- Spring Boot 4.1 · React 19 · PostgreSQL로 만들어 Docker와 GitHub Actions로 배포했고, 백엔드 테스트 169개와 화면 점검 113개로 검증해요.

**근거** `README.md`, `docs/기록유니버스-설계.md` · **꼬리 질문** 가장 어려웠던 부분은? → 1번 트러블슈팅(배포 네트워크) 또는 7번(공개 조건)

### 2. MVP 범위는 어떻게 정했나요?
**답변 핵심**
- 1단계에서 요구사항을 **ID(U-01, P-02 …)로 쪼개** 명세했고, 지금 104개예요. "2주 안에 실제로 접속 가능한 상태"를 목표로 두고, 외부 연동이 필요하거나(소셜 로그인, 메일) 데이터 구조가 커지는 것(알림, 구독)은 **2차 범위로 이유와 함께** 분리했어요.
- 다중 블로그는 MVP에서 열지 않되, DB는 처음부터 **회원:블로그 = 1:N**으로 만들어 나중에 테이블 변경 없이 확장할 수 있게 했어요.

**근거** `요구사항.md` 6장(2차 범위), 5.1(확장성) · **꼬리 질문** 2차로 미룬 것 중 가장 먼저 할 것은? → 알림(받은 캡슐 개봉 알림과 연결)

### 3. 독창 기능 "기록 유니버스"는 왜, 어떻게 정했나요?
**답변 핵심**
- 다른 조가 AI 문서 업로드, 게임화를 했기 때문에 **서비스 이름 "나만의 기록(Own Log)"을 기능으로 보여 주는 것**을 기준으로 골랐어요.
- 시간 축(타임캡슐, 잔디)과 연결 축(`[[링크]]`, 그래프)으로 나누고, **단계마다 배포까지 끝내서 어디서 멈춰도 발표할 수 있게** 4단계로 진행했어요.

**근거** `docs/기록유니버스-설계.md` 1–2장 · **꼬리 질문** 왜 AI 기능은 넣지 않았나? → 외부 API 비용·키 관리, 다른 조와의 차별화

### 4. 2주 일정은 어떻게 관리했나요?
**답변 핵심**
- 기획 → ERD·API 명세 → 백엔드 → 프론트 → 배포의 **5단계**로 나누고, 코딩 전에 **API 명세(요청·응답·에러)를 먼저 확정**했어요(API First). 그래서 프론트 작업 때 응답 형식이 흔들리지 않았어요.
- 일정이 밀린 4단계부터는 작업 단위를 키우고, 대신 **자동 검증(테스트·화면 점검)을 먼저 붙여서** 속도와 품질을 같이 잡았어요.

**근거** `요구사항.md` 7장(일정), `CLAUDE.md` 7장(완료 기준)

### 5. AI 코딩 도구(Claude Code)를 어떻게 활용했나요? 본인의 역할은 무엇인가요?
**답변 핵심** *(가장 많이 물어볼 수 있는 질문이라 솔직하게 준비해요)*
- Claude Code를 **페어 프로그래머**로 썼어요. 저는 **요구사항과 정책 결정**(예: 비공개 카테고리 글 처리, 받는 사람 캡슐 규칙), **설계 승인**, **검증 기준 정의**, **결과 검토와 방향 수정**을 맡았어요.
- AI가 멋대로 하지 않도록 `CLAUDE.md`에 작업 권한(삭제·DB 변경·배포 설정은 먼저 확인), 코드 규칙, **완료 기준**(권한 테스트, 문서 동기화)을 정해 두고 지키게 했어요.
- AI가 만든 코드도 **테스트와 화면 점검으로 검증**했고, 실제로 AI의 수정이 틀린 걸 자동 점검이 잡아낸 적이 있어요(트러블슈팅 10번).

**근거** `CLAUDE.md`, `docs/트러블슈팅.md` 10번 · **꼬리 질문** AI가 만든 코드를 어떻게 이해하고 책임지나? → 아래 질문들을 근거 파일과 함께 설명할 수 있는 것이 그 답이에요

### 6. 다시 처음부터 만든다면 무엇을 다르게 하겠어요?
**답변 핵심**
- **업로드 파일 소유자 테이블**을 처음부터 둘 거예요. 소유자를 기록하지 않아서 생긴 보안 문제를 "참조 확인"으로 막았지만(트러블슈팅 3번), 근본 해결은 아니에요.
- **Refresh Token**과 요청 횟수 제한을 MVP에 넣고, 화면 점검(E2E)을 백엔드 테스트처럼 **처음부터** 만들었을 거예요.

## B. 데이터베이스와 설계

### 7. ERD에서 가장 신경 쓴 부분은 무엇인가요?
**답변 핵심**
- **확장성**: 회원:블로그를 1:N으로 두고, 글·카테고리는 회원이 아니라 **블로그**를 참조해요. "1인 1블로그"는 DB가 아니라 가입 서비스에서만 제한해요.
- **정합성을 DB에서도 보장**: 발행 글은 제목·본문·발행 시각 필수(CHECK), 기본 카테고리 1개(부분 UNIQUE 인덱스), 좋아요 1인 1회(복합 PK).

**근거** `docs/ERD.md` 3장, `V1__init.sql` · **꼬리 질문** 다중 블로그를 열면 무엇을 바꾸나? → `blogs.slug` 컬럼과 생성 API, 주소 체계만

### 8. 소프트 삭제와 하드 삭제를 어떻게 나눴나요?
**답변 핵심**
- **회원은 소프트 삭제**: 아이디는 남겨 기존 링크·댓글 작성자 표시를 보호하고, 이메일·닉네임·비밀번호·사진은 **익명화**해요(개인정보는 남기지 않음).
- **글은 하드 삭제**: 댓글, 좋아요, 북마크, 태그 연결, 글 연결(`post_links` 양방향), 신고까지 **참조하는 쪽부터 순서대로** 지워요. FK에 CASCADE를 쓰지 않고 순서를 코드에 명시했어요.

**근거** `docs/ERD.md` 5장, `PostService.delete`, `WithdrawalCleaner` · **꼬리 질문** CASCADE를 안 쓴 이유는? → 무엇이 지워지는지 코드에서 보이게, 실수로 대량 삭제되지 않게

### 9. 타임캡슐을 컬럼 하나로 구현했다는데 어떻게요?
**답변 핵심**
- 새 컬럼은 `sealed_at`(봉인 시각) 하나예요. 타임캡슐의 `published_at`에는 **개봉 시각(미래)**을 넣어요.
- 공개 조건에 `published_at <= now()` **한 줄**만 더하면 모든 목록에서 봉인 글이 빠지고, **스케줄러 없이** 시각이 지나면 저절로 공개돼요. 정렬도 `published_at DESC` 그대로라 열리는 순간 최신 글 맨 위에 나타나요.

**근거** `V2__time_capsule.sql`, `PostCardQueries.PUBLIC_CONDITION` · **꼬리 질문** DB 시계와 서버 시계가 다르면? → 목록은 DB 시계, 상세는 서버 시계라 몇 초 차이가 날 수 있고, 화면은 재시도 간격을 늘려 대응해요(1.5초 → 3초 → … 최대 30초)

### 10. `[[글]]` 링크는 어떻게 저장하고, 권한은 어디서 검사하나요?
**답변 핵심**
- 글을 **발행·수정할 때** 본문에서 `[[번호|글자]]`를 파싱해 `post_links(source, target)`에 다시 저장해요. 코드 블록 안은 제외하고, 최대 50개, 자기 자신·없는 글·임시저장 글은 저장하지 않아요.
- 권한은 **저장할 때가 아니라 읽을 때** 검사해요. 글이 나중에 비공개가 돼도 링크 데이터는 그대로 두고, 보는 사람 기준으로 "볼 수 없는 글"이면 **제목도 주지 않아요**.

**근거** `PostLinkParser`, `PostLinkService.linkTargets`, `V3__post_links.sql` · **꼬리 질문** 제목 대신 번호로 링크한 이유는? → 제목은 중복·변경될 수 있어요

### 11. 인덱스는 어떻게 설계했고, 빠진 인덱스는 어떻게 찾았나요?
**답변 핵심**
- 조회 패턴마다 인덱스를 맞췄어요: 메인 최신 `(status, visibility, published_at DESC)`, 블로그 목록 `(blog_id, status, published_at DESC)`, 타임캡슐은 **부분 인덱스** `WHERE sealed_at IS NOT NULL`, 백링크 `(target_post_id)`.
- 전체 점검에서 `EXPLAIN`으로 **댓글 `parent_id`에 인덱스가 없어** 댓글 삭제마다 표 전체를 훑는 걸 찾았어요. 새 마이그레이션이 필요한 변경이라 결정을 받아 다음 버전에 넣기로 했어요.

**근거** `docs/ERD.md` 4장, `docs/점검-보고서.md` 2장

### 12. CHECK 제약을 많이 쓴 이유는요?
**답변 핵심**
- 서비스 코드에 버그가 있어도 **DB가 마지막으로 막게** 하려고요. 예: 받는 사람이 있는 캡슐은 반드시 타임캡슐이고 비공개여야 해요(`ck_posts_recipient_capsule`). 봉인 시각은 개봉 시각보다 앞이어야 해요(`ck_posts_capsule_order`).
- 엔티티에서도 같은 규칙을 강제해요(받는 사람이 있으면 공개 범위를 PRIVATE로 고정). 규칙이 두 겹이에요.

**근거** `V2`, `V4` 마이그레이션, `Post.apply`

### 13. Flyway를 쓴 이유와 운영 원칙은요?
**답변 핵심**
- 스키마를 코드처럼 버전 관리하려고 썼어요. JPA는 `ddl-auto: validate`로 **검사만** 해요. 부분 인덱스·CHECK·함수 인덱스처럼 JPA로 만들 수 없는 것도 SQL로 관리해요.
- 원칙: **배포된 마이그레이션은 절대 고치지 않고 새 버전을 추가**해요. 이미 저장된 데이터의 정리(V5)도 마이그레이션으로 해요.

**근거** `db/migration/V1~V5`, `docs/트러블슈팅.md` 8번

### 14. 태그는 대소문자를 어떻게 처리하나요?
**답변 핵심**
- 처음 만든 표기를 저장하고, 비교는 소문자로 해요. 중복은 `lower(name)` **함수 UNIQUE 인덱스**와 `INSERT ... ON CONFLICT`로 막아서, 동시에 같은 태그를 만들어도 하나만 생겨요.
- 점검 때 "비공개 글에만 있는 태그의 저장 표기가 응답에 드러나는" 작은 노출을 찾아, 공개 글이 있을 때만 저장된 표기를 돌려주게 고쳤어요.

## C. Spring Boot · JPA

### 15. N+1 문제는 어떻게 막았나요?
**답변 핵심**
- **목록**은 엔티티 대신 `select new ...PostCardRow(...)` DTO 프로젝션으로 필요한 컬럼만 한 쿼리로 가져와요(본문은 읽지 않아요).
- **상세**는 `join fetch`로 블로그·작성자·카테고리·토픽·태그를 한 번에 가져와요. 연관관계는 모두 LAZY예요.
- 링크 대상처럼 여러 글이 필요한 곳은 `where p.id in :ids` + fetch join으로 한 번에 가져와요.

**근거** `PostCardQueries`, `PostRepository.findDetailById`, `findAllForLinks` · **꼬리 질문** 컬렉션 fetch join과 페이징을 함께 쓰면? → 메모리 페이징 문제가 있어 목록은 DTO 프로젝션을 썼어요

### 16. `open-in-view`를 끈 이유는요?
**답변 핵심**
- 켜 두면 DB 커넥션을 **요청이 끝날 때까지** 붙잡아요. 끄면 서비스 트랜잭션 안에서 DTO를 모두 만들어야 해서, 지연 로딩이 컨트롤러로 새는 걸 **구조적으로** 막을 수 있어요. 점검에서도 엔티티가 컨트롤러로 넘어가는 경로는 없었어요.

### 17. 조회수·좋아요의 동시성 문제는 어떻게 해결했나요?
**답변 핵심**
- "읽고 → +1 → 저장"은 동시 요청에서 값이 사라져요(Lost Update). 그래서 **DB가 직접 더하게** 했어요: `UPDATE posts SET like_count = like_count + 1`.
- 엔티티의 카운터 필드는 `insertable/updatable = false`로 막았어요. Hibernate는 수정할 때 모든 컬럼을 UPDATE하기 때문에, 이렇게 하지 않으면 제목 수정이 예전 조회수로 덮어써요.
- 좋아요 중복은 복합 PK + `ON CONFLICT DO NOTHING`, **실제로 들어간 행이 1개일 때만** 수를 올려요.
- 검증: 16개 스레드로 100명 동시 좋아요 → 정확히 100, 1명 10번 연타 → 1, 방문자 50명 동시 조회 → 50.

**근거** `LikeConcurrencyTest`, `ViewCountConcurrencyTest` · **꼬리 질문** 비관적 락이나 낙관적 락은 왜 안 썼나? → 단순 증감은 원자적 UPDATE가 가장 싸고 충돌·재시도가 없어요

### 18. 파일 삭제는 트랜잭션과 어떻게 맞췄나요?
**답변 핵심**
- 파일은 롤백할 수 없어서, DB가 **커밋된 뒤에만** 지워요(`@TransactionalEventListener(phase = AFTER_COMMIT)`). 롤백되면 이벤트가 실행되지 않아 "DB는 그대로인데 이미지만 사라지는" 일이 없어요.
- 점검 뒤로는 지우기 전에 다른 회원·글이 같은 파일을 쓰는지도 확인해요.

**근거** `ImageDeleteListener`, `ImageReferenceChecker`

### 19. 예외 처리 구조를 설명해 주세요.
**답변 핵심**
- 모든 에러는 `{ code, message, fieldErrors }` 한 형식이에요. 비즈니스 규칙 위반은 `ErrorCode` enum + `BusinessException`, 입력 검증 실패는 칸별 `fieldErrors`로 바꿔요(`GlobalExceptionHandler`).
- **DB 제약 위반도 의미 있는 에러로** 바꿔요: UNIQUE 위반(동시 가입 등)은 409, 삭제와 동시에 들어온 요청의 FK 위반은 404. 모르는 위반은 500으로 두고 로그만 남겨요.
- 메시지는 화면에 바로 보여 줄 문장이고, 계정 존재 여부나 내부 정보는 담지 않아요.

**근거** `global/error/*`, `ForeignKeyErrorMappingTest`

### 20. 403과 404는 어떻게 구분하나요?
**답변 핵심**
- **볼 수 없는 대상이면 404**(존재 자체를 숨겨요), **볼 수는 있지만 권한이 없으면 403**이에요. 남의 비공개 글 수정은 404, 남의 공개 글 수정은 403이에요.
- 받는 사람이 열린 편지를 고치려 하면 볼 수는 있으니 403이에요(점검에서 404로 잘못 나가던 걸 고쳤어요).

**근거** `docs/API명세서.md` 1.3, `PostService.getPostForOwner`

### 21. 비공개 글이 새지 않게 어떻게 보장했나요?
**답변 핵심**
- 공개 판단을 **두 곳**에만 뒀어요: 목록 쿼리는 `PUBLIC_CONDITION` 상수, 엔티티는 `Post.isViewableBy(회원)`. 모든 기능이 이걸 재사용해요.
- 그래서 타임캡슐을 추가할 때 JPQL 목록 쿼리 6개는 고치지 않았고, 따로 적혀 있던 네이티브 SQL(사이드바 글 수) 1곳만 고쳤어요. 받는 사람 캡슐도 메서드에 조건 하나를 더해서 댓글·좋아요·링크까지 적용됐어요.
- 기능마다 **"새는 경로" 테스트**(목록, 검색, 태그, 링크 미리보기, 그래프, 잔디)를 둬요.

**근거** `docs/트러블슈팅.md` 7번 · **꼬리 질문** 네이티브 SQL은? → 사이드바 글 수·잔디는 따로 적혀 있어서 CLAUDE.md 규칙으로 함께 고치게 했어요(남은 약점으로 인지하고 있어요)

### 22. 커스텀 검증 어노테이션을 만든 적이 있나요?
**답변 핵심**
- `@MaxUtf8Bytes`예요. BCrypt는 72바이트까지만 받는데 비밀번호 규칙은 글자 수(64자)만 봐서, 한글 비밀번호가 500 에러를 냈어요. `ConstraintValidator`로 UTF-8 바이트 수를 검사해서 400과 칸별 메시지로 바꿨어요.

**근거** `global/validation/MaxUtf8Bytes*`, 트러블슈팅 5번

### 23. 시간대는 어떻게 다뤘나요?
**답변 핵심**
- 저장은 `TIMESTAMPTZ` + 엔티티 `Instant`(UTC 기준 순간), 응답은 `KstTime.of()`로 `+09:00`을 붙여요. 날짜 계산(잔디, "그날의 기록")은 `Asia/Seoul` 기준으로 하고, KST 자정 경계(14:59Z/15:00Z)를 테스트해요.
- 배포 컨테이너는 `TZ=Asia/Seoul`이지만 코드는 시간대 설정에 기대지 않아요.

**근거** `KstTime`, `ActivityApiTest.groupsByKstDate`

## D. 보안과 인증

### 24. JWT를 localStorage에 둔 이유와 위험 대응은요?
**답변 핵심**
- 쿠키 방식은 CSRF 대응과 서버 설정이 더 필요해서, MVP에서는 **localStorage + Authorization 헤더**를 골랐어요. 대신 가장 큰 위험인 **XSS를 전제 조건으로 막았어요**: 마크다운은 `rehype-sanitize`를 거쳐서만 그리고, `dangerouslySetInnerHTML`은 쓰지 않아요.
- 이 결정과 전제는 요구사항 8장에 기록했고, 2차에서 Refresh Token(HttpOnly 쿠키)과 함께 다시 볼 거예요.

**꼬리 질문** XSS가 뚫리면? → 토큰 탈취 가능. 그래서 sanitize 우회 경로(커스텀 링크 플러그인 포함)를 점검에서 따로 확인했어요

### 25. JWT 인증 흐름과 로그아웃은요?
**답변 핵심**
- 로그인하면 Access Token(2시간)을 발급해요. 필터가 서명(jjwt `verifyWith`)을 검증하고, **요청마다 회원 상태를 확인해서 탈퇴한 회원의 토큰은 만료 전이라도 거부**해요.
- 로그인 실패는 이메일·비밀번호 중 무엇이 틀렸는지 구분하지 않고, 없는 이메일이어도 **더미 해시로 BCrypt를 한 번 돌려서** 응답 시간으로 가입 여부를 알 수 없게 했어요.
- Refresh Token이 없어서 로그아웃은 클라이언트가 토큰을 지우는 방식이에요(한계로 인지).

**근거** `JwtTokenProvider`, `JwtAuthenticationFilter`, `AuthService.login`

### 26. 실제로 찾은 보안 취약점을 하나 설명해 주세요. (인증 우회)
**답변 핵심**
- `/%61pi/users/me`로 보내면 로그인 검사를 건너뛰었어요. 인가 규칙은 **디코딩 전 주소**(`getRequestURI`)로 "API가 아니다"라고 판단했고, MVC는 **디코딩 후 주소**로 API 컨트롤러를 찾았어요. 운영 서버에서도 재현됐어요.
- MVC와 같은 방식으로 해석하는 경로 패턴(`/api/**`)으로 바꾸고, MockMvc가 주소를 다시 인코딩하지 않게 `URI.create`로 원래 주소를 보내는 회귀 테스트를 남겼어요.

**근거** 트러블슈팅 2번, `SecurityAuditTest`

### 27. IDOR 사례가 있었나요?
**답변 핵심**
- 프로필 사진 주소에 **남의 이미지 주소**를 넣었다가 바꾸면 그 파일이 지워졌어요. 업로드 소유자를 기록하지 않은 게 원인이었어요.
- 마감이 가까워서 "다른 회원·글이 쓰는 파일은 지우지 않는다"로 막고, 소유자 테이블은 2차로 미뤘어요. **선택지 세 개를 비교한 이유**를 문서에 남겼어요.

**근거** 트러블슈팅 3번

### 28. 오픈 리다이렉트는 어떻게 막았나요?
**답변 핵심**
- `//` 검사만으로는 `/` + 탭 + `/evil.com`을 못 막았어요. 브라우저가 탭을 지우고 `//evil.com`으로 해석하기 때문이에요.
- **`new URL()`로 실제로 해석해서 출처(origin)를 비교**하고, 경로 부분만 쓰게 바꿨어요. 화면 점검에서 공격 주소 세 가지를 확인해요.

**근거** 트러블슈팅 4번, `LoginPage.safeRedirect`

### 29. 이미지 업로드는 어떻게 검증하나요?
**답변 핵심**
- 크기(5MB) → 확장자 → **파일 앞 12바이트(매직 넘버)**로 실제 형식(JPEG·PNG·GIF·WEBP)을 확인해요. 클라이언트가 보낸 Content-Type과 파일 이름은 믿지 않아서 SVG·스크립트 위장을 막아요.
- 저장 이름은 UUID, 확장자는 실제 내용 기준, 삭제할 때 `../` 경로 조작을 막아요.
- 한계: 크기 줄이기·EXIF(위치 정보) 제거가 없어서 다음 버전 계획에 있어요.

**근거** `ImageService`, `ImageType`, `LocalStorageService`

### 30. SQL 인젝션과 LIKE 검색은요?
**답변 핵심**
- 모든 쿼리는 파라미터 바인딩이에요. 검색어는 `%`, `_`, `\`를 **이스케이프**해서 글자 그대로 찾고(`LikePattern`), `escape '\'`를 함께 써요. 탈퇴 정리 SQL처럼 문자열을 이어 붙이는 곳은 상수만 이어요.

### 31. 비밀값은 어떻게 관리했나요?
**답변 핵심**
- DB·SSH 비밀번호, JWT 비밀키는 **GitHub Secrets**와 로컬 `.env`(커밋 금지)에만 있어요. 배포 스크립트는 `-e 이름`만 넘겨서 명령 기록에 값이 남지 않고, 로그에는 Secret 이름만 출력해요.
- JWT 비밀키가 없으면 서버에서 한 번 만들어 파일 권한 600으로 보관해요.

**근거** `deploy/deploy.sh`, `.github/workflows/deploy.yml`

### 32. 공개 범위 규칙이 복잡한데, 받는 사람 캡슐의 보안 규칙은요?
**답변 핵심**
- 받는 사람이 있는 캡슐은 **항상 비공개**(엔티티와 DB CHECK 두 겹)라서 공개 목록·검색·우주에 저절로 나오지 않아요.
- 열람: 보낸 사람은 언제나, **받는 사람은 열린 뒤에만**, 그 밖의 사람에게는 404. 받는 사람은 열리기 전에 잠금 카드만 받아요. 점검에서 보낸 사람의 **비공개 카테고리 이름**이 받는 사람에게 보이는 걸 찾아 가렸어요.

**근거** `RecipientCapsuleApiTest`, `SecurityAuditTest`

## E. 성능

### 33. 프론트 번들 크기는 어떻게 줄였나요?
**답변 핵심**
- 무거운 화면을 `React.lazy`로 나눴어요: 글쓰기(마크다운 에디터), 기록 우주(d3-force), 글 상세(react-markdown + sanitize). 메인 번들이 **492KB → 354KB**(gzip 155KB → 113KB)로 줄었어요.
- 지연 로딩의 부작용(배포 뒤 예전 파일이 사라져 화면이 하얗게 되는 문제)은 **오류 경계 + 한 번 새로고침**으로 막았어요.

### 34. 기록 우주(그래프)의 성능은 어떻게 다뤘나요?
**답변 핵심**
- 서버: 별 최신 300개(전체 우주 500개), 태그 선 1,000개(1,500개) **상한**을 둬서 쿼리와 화면이 커지지 않게 했어요.
- 화면: 수백 개 노드를 **SVG 대신 Canvas**로 그리고, d3-force는 배치 계산만 해요. 타임랩스 값은 React state가 아니라 캔버스에 직접 전달해서 **페이지 다시 그리기를 0회**로 줄였어요.

**근거** `GraphService`, `UniverseCanvas`, 트러블슈팅 11번

### 35. 검색은 확장성이 있나요?
**답변 핵심**
- 지금은 `ILIKE '%…%'`라서 글이 많아지면 본문 전체를 훑어요(점검에서 확인). 현재 규모에서는 문제없어서, `pg_trgm` GIN 인덱스나 전문 검색을 2차로 계획했어요. 공개 API라 요청 횟수 제한도 함께 필요해요.

### 36. 조회수를 올리는 상세 API의 락 문제는요?
**답변 핵심**
- 조회수 UPDATE가 행 락을 잡은 채 좋아요 여부 조회 등이 이어져서, 인기 글에 동시 조회가 몰리면 대기가 생길 **가능성**을 점검에서 짚었어요(측정한 건 아니에요). UPDATE를 마지막으로 옮기거나 짧은 트랜잭션으로 분리하는 개선안을 남겼어요. 지금 규모에서는 영향이 없어요.

## F. 프론트엔드 (React)

### 37. `useEffectEvent`는 왜 썼나요?
**답변 핵심**
- 이펙트 안에서 **최신 props·state는 읽되, 그 값이 바뀔 때마다 이펙트를 다시 실행하지는 않게** 하려고요. 예: `useAsync`는 `key`가 바뀔 때만 다시 불러오고, 불러오는 함수는 매 렌더링 새로 만들어져도 괜찮아요. React 19.2에서 공식 API가 됐어요.

**근거** `hooks/useAsync.js`, `SealedCapsule`

### 38. 비동기 요청의 경쟁 상태는 어떻게 처리했나요?
**답변 핵심**
- `useAsync`는 이펙트 정리 함수에서 `ignore = true`로 바꿔 **늦게 도착한 예전 응답을 버려요.** 탭을 빠르게 바꿔도 마지막 요청의 결과만 보여요.
- 좋아요처럼 응답으로 화면을 고치는 곳은 **응답이 같은 글일 때만** 반영해요(다른 글로 이동한 뒤 도착한 응답이 섞이지 않게).

### 39. 마크다운 XSS와 `[[링크]]` 렌더링은 어떻게 했나요?
**답변 핵심**
- `react-markdown` + `rehype-sanitize`로 스크립트·위험한 속성을 제거해요.
- `[[번호|글자]]`는 **remark 플러그인**으로 마크다운 트리(AST)만 링크 노드로 바꿔요. HTML 문자열을 만들지 않으니 뒤에 오는 sanitize가 그대로 동작해요. 코드 블록 안은 텍스트 노드가 아니라 자연히 제외돼요(서버 파서와 같은 규칙).

**근거** `utils/remarkPostLinks.js`, `components/MarkdownView.jsx`

### 40. state 대신 ref를 쓴 경우가 있나요?
**답변 핵심**
- "두 번 클릭 방지"를 state로 했더니, 같은 순간 두 번 누르면 두 이벤트 모두 **같은 렌더링의 `false`**를 봐서 둘 다 통과했어요. 화면 점검이 이걸 잡아냈고, **즉시 바뀌는 `useRef`**로 판단하고 state는 버튼 표시에만 쓰게 고쳤어요.

**근거** 트러블슈팅 10번

### 41. 401 처리를 어떻게 설계했나요?
**답변 핵심**
- axios 인터셉터가 401(`UNAUTHORIZED`)이면 토큰을 지우고 원래 주소를 기억한 채 로그인 화면으로 보내요. 그런데 **세션 복원 요청까지 잡아서** 만료 토큰으로 공개 화면에 들어와도 튕기는 버그가 있었어요.
- 요청별 `skipAuthRedirect` 옵션을 두고, 네트워크 오류·배포 중(502)에는 토큰을 지우지 않게 해서 **401일 때만** 로그아웃해요.

**근거** `api/client.js`, `auth/AuthProvider.jsx`, 트러블슈팅 9번

### 42. 같은 컴포넌트가 다른 주소에 쓰일 때 상태 문제는요?
**답변 핵심**
- `/write`와 `/write/:postId`가 같은 컴포넌트라, 글을 바꿔도 이전 글 상태가 남았어요. **`key`로 글이 바뀌면 새로 그리되**, 처음 임시저장해서 주소만 `/write/{id}`로 바뀔 때는 `location.state`로 같은 key를 유지해서 **쓰던 내용을 덮어쓰지 않게** 했어요.

**근거** `App.jsx`의 `WriteRoute`, `e2e/check-audit`

### 43. 디자인과 반응형은 어떻게 관리했나요?
**답변 핵심**
- Tailwind 4의 `@theme`에서 **팔레트 변수만 바꿔** 기존 클래스 전체를 브랜드 색으로 바꿨어요(코드 수정 최소화). 우주 배경은 이미지 없이 CSS 그라데이션으로 그렸어요.
- 375px 화면에서 **가로 스크롤이 생기지 않는지** 화면 점검으로 매번 확인하고, 한글은 `word-break: keep-all`로 단어 중간에서 끊기지 않게 했어요.

## G. 테스트

### 44. 테스트 전략은 무엇인가요? 왜 단위 테스트보다 통합 테스트가 많나요?
**답변 핵심**
- 백엔드는 **Testcontainers(실제 PostgreSQL) + MockMvc 통합 테스트** 위주예요(169개). 이 프로젝트의 위험은 공개 조건 누수, 동시성, 부분 인덱스·CHECK 같은 **DB와 맞물린 규칙**이라, Mock으로는 잡을 수 없는 버그가 많아요.
- 순수 로직(링크 파서, 요약 규칙, 외래키 매핑)은 단위 테스트로 빠르게 검증해요.
- 기능마다 **권한 케이스(남의 것·비공개·비로그인)**를 완료 기준에 넣었어요.

**근거** `IntegrationTest`, `CLAUDE.md` 7장

### 45. 동시성 테스트는 어떻게 작성했나요?
**답변 핵심**
- `ExecutorService`(16 스레드)와 `CountDownLatch`로 **동시에 출발**시키고, 끝난 뒤 DB 값을 확인해요. 회원 100명 동시 좋아요 → 100, 한 회원 10번 연타 → 1, 50명 동시 조회 → 50.

**근거** `LikeConcurrencyTest`, `ViewCountConcurrencyTest`

### 46. 화면 테스트(E2E)는 어떻게 했나요?
**답변 핵심**
- Playwright 대신 **Chrome DevTools Protocol을 직접** 쓰는 작은 도우미를 만들어 추가 설치 없이 돌려요(12종 113개 항목). 375px 반응형, 카운트다운 0초 자동 개봉, 업로드까지 실제로 확인해요.
- 처음엔 브라우저 프로필을 공유해서 결과가 흔들렸어요. **실행마다 새 프로필**로 격리했고, 시연 DB를 더럽히지 않게 **배포 이미지를 별도 DB 스키마로 띄워** 운영과 같은 조건에서 점검해요.

**근거** `e2e/README.md`, 트러블슈팅 12번

### 47. 테스트가 실제로 버그를 잡은 사례가 있나요?
**답변 핵심**
- 세 가지가 있어요: ① 만료 토큰 튕김(트러블슈팅 9번)은 테스트 불안정을 파고들다 발견했어요. ② 두 번 클릭 방지 수정이 틀렸다는 걸 화면 점검이 `0 → 2`로 잡았어요. ③ 잔디가 캡슐을 봉인한 날 세는데 방문자 목록엔 그 글이 없어 **숫자와 목록이 어긋나는** 것을 점검이 잡아 "이날 봉인한 타임캡슐" 표시를 추가했어요.

## H. 배포 · 운영 · 협업

### 48. 배포 과정을 설명해 주세요.
**답변 핵심**
- 화면(React 빌드)과 API를 **Docker 이미지 하나**로 만들어(멀티 스테이지 빌드), Spring이 정적 파일과 SPA 주소(새로고침해도 화면)를 함께 제공해요.
- `main`에 병합하면 GitHub Actions가 **테스트 → 이미지 빌드 → scp 전송 → SSH로 `deploy.sh` 실행**까지 해요. 스크립트는 DB 연결부터 확인하고, 새 컨테이너가 응답할 때까지 기다린 뒤 예전 이미지를 정리해요. 업로드 파일은 볼륨에 둬서 배포해도 남아요.
- 앞단은 수업 공용 Nginx가 도메인과 HTTPS를 맡아요.

**근거** `Dockerfile`, `deploy/deploy.sh`, `.github/workflows/deploy.yml`

### 49. 배포 중 가장 어려웠던 문제는요?
**답변 핵심**
- 컨테이너가 DB에 "연결 시간 초과"였는데, 처음엔 Secret 값을 의심했어요. 같은 오류가 반복되자 **배포 스크립트가 서버와 컨테이너 양쪽에서 DB 연결을 직접 시험**하게 바꿨고, `서버 OK / 컨테이너 FAIL`로 Docker 기본 네트워크에서 학교 내부망으로 가는 경로가 막힌 걸 찾았어요. `--network host`로 해결했고, 진단 단계는 계속 남겨 뒀어요.

**근거** 트러블슈팅 1번

### 50. 1인 개발인데 Git Flow와 버전 관리를 도입한 이유는요?
**답변 핵심**
- `main`에 푸시하면 바로 배포되는 구조라, **작업 중인 코드와 운영(발표) 버전을 분리**할 필요가 있었어요. `main`(운영) / `develop`(통합) / `feature`·`release`·`hotfix`로 나눴고, 커밋은 Conventional Commits(이미 100% 지키고 있었어요), 버전은 SemVer와 `CHANGELOG.md`(Keep a Changelog)로 관리해요.
- 지난 이력에는 단계별 태그(`v0.1.0` ~ `v0.6.0`)를 붙이고, `release/1.0.0`으로 첫 정식 릴리스를 해서 Git Flow를 한 바퀴 돌렸어요. 발표 직전 버그는 `hotfix/1.0.x`로만 고쳐요. 이력은 다시 쓰지 않고 force push를 금지해요.

**근거** `CLAUDE.md` 11장, `CHANGELOG.md`, `git log --graph`
